# 관리자 완료 · 2026-11-04

사용자 승인: 기존 진행 주문 146건을 운영상 종료한다. 제작·입금·배송 기록을 보존하고 고객 알림을 보내지 않는다. 이후 새 주문은 포함하지 않는다.

주문 보관과 결제/배송 상태를 구분하는 기존 운영 도구의 패턴을 따른다. 참고: [Shopify 주문 상태](https://help.shopify.com/en/manual/fulfillment/managing-orders/order-status).

## 동작

- `ADMIN_COMPLETED`는 별도 관리자 종료 상태다. lifecycle 주문 상태만 COMPLETED로 닫고, 원래 제작 단계·결제·송장·수령 방식·배송 상태·파일·정산·보관 기간을 그대로 둔다.
- 기존 전체 주문의 완료 탭, 운영 현황의 완료·종료, 완료 주문·AS 목록에 모두 나타난다. 관리자 완료라는 표시로 실제 배송/수령과 구분한다.
- 고객 SMS/알림톡/Telegram, 배송 알림 outbox, 모델 검수 이벤트를 생성하지 않는다. 기존 신청 알림 설정/코드를 변경하지 않는다.
- 작업 생성/완료·물리 출력·실제 배송 완료·새 보관 기간 시작으로 해석하지 않는다. 제작 이력을 가짜 완료로 덮어쓰지 않는다.

## API

`POST /api/admin/orders/administrative-completions`

```json
{
  "orders": [{"orderNumber": "주문번호", "version": 0}],
  "reason": "기존 주문 정리"
}
```

- 기존 Bearer 인증, OWNER 역할, OVERRIDE_WORKFLOW + VIEW_ALL_ORDERS + VIEW_ORDER_BASIC 권한 필수.
- Idempotency-Key 필수. 기존 workflow command·계정 잠금·주문 버전 검증·트랜잭션 재사용.
- 1~200건의 명시적 주문 목록만 처리. 현재 ACTIVE + NOT_READY이며 PAYMENT_COMPLETED/IN_PRODUCTION/LEGACY_FREE인 주문만 허용. 미입금/취소/환불/이미 발송된 주문을 완료로 만들지 않는다.
- 전체 대상 검증 후 저장. 한 건이라도 누락/중복/버전 충돌/처리 불가이면 전체 중단.
- 전후 상태를 workflow 감사 이력과 기존 주문 상태 이력에 저장. 응답의 operationId 및 전후 상태를 프론트에서 JSON으로 내려받을 수 있다.

`POST /api/admin/orders/{orderNumber}/restore-administrative-completion`

```json
{"version": 1, "reason": "잘못 완료한 주문 복구"}
```

같은 소유자/권한/멱등성/버전 검증을 적용한다. 현재 관리자 완료인 주문만 최신 ADMIN_COMPLETE 감사 이력의 정확한 이전 상태로 복구한다. 복구도 감사/주문 이력을 남기며 알림은 보내지 않는다. 제작 단계·금액·송장을 임의로 재구성하지 않는다.

## 프론트 연결

운영 현황 상단의 관리자 완료 처리에서 대상을 확인한다. 창을 열 때 버전을 고정하고 주문번호를 명시한다. 새로운 주문을 목록에 자동 추가하지 않는다. 완료 후 변경 기록을 다운로드할 수 있다. 완료·종료에서 주문을 선택하면 소유자에게 개별 복구 버튼이 나타난다.

## 배포·복구

- DB 스키마 변경/자동 데이터 마이그레이션 없음. 배포만으로 주문이 바뀌지 않는다.
- 백엔드 먼저 배포하고 프론트 연결 후 승인된 대상만 UI에서 실행한다.
- 양쪽 저장소에 `backup/admin-completion-before-20261104` 태그와 로컬 소스 아카이브를 보존한다.
- **코드만 먼저 과거로 되돌리지 않는다.** 관리자 완료 데이터가 생긴 뒤에는 이전 백엔드가 새 enum을 읽지 못한다. 먼저 승인한 범위의 관리자 완료를 감사 이력 기반으로 복구하고 ADMIN_COMPLETED가 없는지 확인한 뒤 이전 코드를 배포한다. 복구되지 않은 데이터가 있으면 새 enum을 읽는 백엔드를 유지한다.
- 사용자 데이터가 있는 전후 기록/대상 파일은 공개 저장소에 넣지 않는다. 실제 대상과 실행 결과는 별도 로컬 운영 백업 폴더에 둔다.

## 검증

통합 테스트에서 소유자 권한, 전체 선택의 원자성, 미입금·중복·버전 충돌 거부, 동일 요청 재시도, 제작/입금/배송/파기 기준일 보존, 알림 outbox 미생성, 완료 목록 노출 및 감사 이력 기반 복구를 확인한다. 프론트는 새 주문 제외·중복 입력 차단·권한에 따른 버튼 노출·명시된 번호만 API로 전달하는 E2E를 실행한다.
