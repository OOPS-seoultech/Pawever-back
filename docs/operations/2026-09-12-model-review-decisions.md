# 모델 검수 승인·수정 요청

첫 운영 배포에 이어 검수 결정을 구현한다. 근거는 원본 운영 명세 8.2·9.4, 최종 이관서 9.2·9.7이다. 성공 기준은 수정 요청 → 새 모델링 시도 → 새 파일 제출 → 재검수 → 승인 → 색상 작업 대기가 기존 이력과 결제 정보를 보존하며 동작하는 것이다.

- [x] 기존 첫 인계와 서버 권한·파일 계약 확인, 미구현 API 실패 테스트 작성.
- [x] 승인·수정 요청 API, 검수 이력과 새 작업 생성 구현.
- [x] 체크리스트·수정 사유·이전/현재 파일 표시 및 브라우저 검사.
- [ ] 실제 MariaDB 이전·동시 요청·기존 기능 검사, 배포 및 운영 조회 확인.

담당 검수자만 `REVIEW_MODEL`과 필수 자료 권한으로 결정한다. 승인은 닮음·주요 특징·하단 커팅·출력 가능성 확인이 필요하다. 수정 요청은 사유 코드(얼굴 형태, 귀, 꼬리, 자세, 하단 커팅, 출력 가능성, 색상 분리)와 300자 이내의 구체적인 메모를 필수로 받는다. 모든 결정은 주문 version과 멱등 키를 검증한다.

검수한 모델링 task와 검수 결과는 별도 기록으로 보존한다. 수정 요청은 완료된 작업을 덮어쓰지 않고 새 MODELING 작업의 attempt를 증가시켜 MODELING_QUEUE에 둔다. 기존 모델러가 활성 역할을 유지하면 그 사람에게 돌아가며, 그렇지 않으면 미배정으로 남겨 관리자가 지정한다. QC_FAILED 이슈는 수정 작업 자체를 막지 않고 재제출 완료 시 해소하며 검수 사유 이력은 유지한다. 재제출 완료에는 이번 시도의 세 종류 확정 파일을 모두 요구한다.

승인하면 현재 검수 작업을 완료하고 승인자의 COLOR_MAPPING 작업을 생성한다. 이번 완료 경계는 색상 작업 대기까지다. 실제 색상 매핑·출력 기능과 승인 템플릿이 필요한 고객 제작 시작 알림은 다음 범위다. 승인 기록은 이후 알림 연결의 근거로 남기며 임의 고객 메시지를 발송하지 않는다. 과거 주문·계정의 배정은 자동 변경하지 않는다.

검증: 추가 전 검수 API 테스트 5건이 미구현 경로로 실패했고, 화면 테스트 3건이 미구현 버튼 및 이전 파일로 완료 가능한 상태를 검출했다. 구현 후 실제 MariaDB에서 첫 흐름과 검수 API 16건, V17→V18 이전·재적용 1건이 통과했다. 반복 수정·재제출·승인, 동시 승인/수정 중 하나만 반영, 권한·사유·체크리스트·필수 파일 검증, 300자 수정 메모, 중복 키 재사용과 비활성 모델러 미배정을 포함한다. 화면의 기존 4건과 신규 3건도 통과했다.

V18은 model_reviews 테이블만 추가한다. 기존 검수 대기 task와 파일을 그대로 처리하며 사전 승인 결과를 만들지 않는다. 검수 응답은 taskAttempt, modelingTaskId, 회차별 artifact 정보, reviews 이력을 추가한다. 현재 색상 작업을 다른 검수자에게 재배정할 때도 DESIGN_QC 역할을 검사한다.
