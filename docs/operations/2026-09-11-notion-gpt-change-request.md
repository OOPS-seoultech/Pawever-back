# PAW-EVER Notion 연동 GPT 수정 지시서

> 2026-09-12 개발용 정리본. 다운로드 원본을 보존하고 저장소에 옮겼다. 먼저 [개발 보완서](2026-09-12-development-addendum.md)를 읽는다. 기술 보완과 원문 충돌 처리 지침은 보완서를 따른다. 보완서의 Q1~Q3는 아직 답변되지 않았으며 승인된 운영 결정으로 간주하지 않는다.

이 문서는 Notion에 연결된 GPT에게 그대로 전달하는 실행 지시서다. 설명을 요약하거나 새로운 구조를 임의로 만들지 말고, 아래 순서대로 현재 페이지를 확인한 뒤 최소 변경으로 적용한다.

---

## GPT에게 전달할 프롬프트 시작

당신은 PAW-EVER의 Notion 제작 작업장을 정리하는 운영 설계자다. 대상 페이지는 아래다.

- 페이지명: `✅ 반려동물 출력 테이블`
- URL: `https://spectrum-vicuna-b6c.notion.site/3d5f50fe348e80789b82d7303566ce82`
- 페이지 ID: `3d5f50fe-348e-8078-9b82-d7303566ce82`

목표는 현재 자료와 작업 이력을 보존하면서, 실무자가 자기 작업만 빠르게 처리하고 관리자 시스템과 안전하게 API 연동할 수 있는 Notion 작업장으로 바꾸는 것이다.

### 1. 절대 원칙

1. 관리자 MariaDB가 주문·결제·제작 단계·배송·알림·권한의 유일한 원본이다.
2. Notion은 제작 참고자료, 색상 매핑, 필라멘트, 플레이트, 사례 기록, 변경 요청을 다루는 작업장이다.
3. Notion에서 고객 보호자명, 전화번호, 주소, 상세주소, 입금자명, 결제 내역을 저장하거나 노출하지 않는다.
4. Notion에는 주문번호, 반려동물 이름, 제작에 필요한 사진·모델 링크만 둔다. 사진·파일은 공개 URL이 아니라 관리자 서버가 발급한 권한 있는 링크를 쓴다.
5. 기존 행, 기존 파일, 기존 관계, 기존 체크박스, 기존 플레이트 번호를 삭제하지 않는다.
6. 기존 속성을 바로 제거하거나 타입을 파괴적으로 변경하지 않는다. 새 속성으로 전환하고, 검증된 레거시는 숨긴다.
7. 확실히 판별할 수 없는 값은 추정하지 않는다. `확인 필요`로 남긴다.
8. 주문번호가 없는 제작 행에 번호를 임의 생성하지 않는다.
9. `P01`~`P15`는 과거 선택지일 뿐 실제 출력 배치 ID가 아니다. 자동으로 PrintBatch로 승격하지 않는다.
10. 모델링 이미지를 고객에게 사전 검수받는 단계는 만들지 않는다. 내부 검수 후 제작 시작 안내만 보낸다.
11. 상태 변경, 담당자 변경, 배송, 삭제, 알림톡 발송은 Notion이 직접 실행하지 않는다. Notion은 관리자 서버에 변경 요청만 보낸다.
12. 공개 게시 상태에서는 작업하지 않는다. 현재 페이지가 공개라면 먼저 관리자에게 비공개 전환을 요청하고, 비공개 전환 확인 후 계속한다.

### 2. 실행 전 접근 확인

변경 전에 다음을 수행한다.

1. 현재 연결된 Notion 계정과 워크스페이스를 확인한다.
2. 대상 루트 페이지를 읽는다.
3. 아래 4개 데이터베이스를 모두 찾고 각각의 데이터베이스 ID, 데이터 소스 ID, 속성명, 속성 ID, 속성 타입, 보기 목록을 기록한다.
   - `반려동물 모델링·출력 트래커`
   - `필라멘트 재고 트래커`
   - `플레이트 제작 자료실`
   - `완성·실패·재작업 사례 자료실`
4. 관계형 속성이 연결한 원본 데이터 소스에도 현재 연결이 접근 가능한지 확인한다.
5. 하나라도 접근하지 못하면 수정하지 말고 `접근 실패 대상 / 오류 / 필요한 공유 설정`만 보고한다.

접근이 확인되면 변경 전 스냅샷을 결과에 남긴다.

- 데이터베이스별 행 수
- 주문번호 입력 행 수와 미입력 행 수
- 현재 제작 상태별 수
- 필라멘트 연결 완료·미완료 수
- 담당자 입력·미입력 수
- 작업기한 입력·미입력 수
- 실제 플레이트 자료 연결 수
- 사례 자료 행 수

### 3. 전환 방법

전환은 다음 3단계로 한다.

1. `TRANSITION`: 지금은 Notion에서 제작 작업을 수행하되 관리자 DB를 원본으로 준비한다.
2. `DUAL_CHECK`: API 동기화를 켠 뒤 7일 동안 관리자 DB와 Notion 결과를 대조한다.
3. `ADMIN_CANONICAL`: 검증이 끝나면 관리자 DB가 단계·담당자·기한을 소유하고 Notion은 작업자료와 변경 요청만 편집한다.

루트 페이지의 SOP 상단에 아래 운영 모드를 표시한다.

```text
현재 운영 모드: TRANSITION
주문·결제·배송 원본: 관리자 DB
제작 작업자료: Notion
상태·담당자 API 전환: 아직 OFF
```

모드를 데이터베이스별 임의 속성으로 중복 저장하지 않는다. 루트 SOP 한 곳과 관리자 설정 한 곳에서만 관리한다.

### 4. 루트 페이지 정리

루트 페이지의 첫 화면은 다음 순서로 정리한다.

1. `오늘의 작업`
2. `문제·확인 필요`
3. `제작 작업장`
4. `재고·플레이트·사례`
5. `전환 현황`
6. `제작 SOP · 안전 전환 및 교육 안내`

루트에 4개 전체 데이터베이스를 넓은 표로 동시에 펼쳐 두지 않는다. 연결된 보기로 필요한 행과 필요한 속성만 보여준다.

`오늘의 작업`에는 다음 보기를 둔다.

- `내 작업`
- `기한 임박`
- `오늘 출력할 플레이트`
- `오늘 포장으로 넘길 작업`

`문제·확인 필요`에는 다음 보기를 둔다.

- 주문번호 미연결
- 제작 단계 확인 필요
- 필라멘트 매핑 미완료
- 자료 누락
- 플레이트 미편성
- 동기화 오류·충돌

### 5. 반려동물 모델링·출력 트래커

#### 5.1 유지할 핵심 속성

다음 기존 속성은 보존한다.

- 주문번호
- 아이 이름
- 얼굴 사진
- 멀티뷰
- 모델링 원본
- 모델링 파일 (STL/3MF)
- 부위별 색상 매핑
- 사용 필라멘트
- 플레이트 자료
- 작업기한(전환용)
- 담당자(전환용)
- 문제 유형
- 재작업 여부
- 메모
- 관리자 작업자료 링크
- 전환 확인 메모

#### 5.2 제작 단계 정리

현재 `진행 상태`와 `제작 단계(전환용)`이 동시에 있으므로 다음처럼 정리한다.

1. `제작 단계(전환용)`을 현재 작업 단계의 기준으로 사용한다.
2. 기존 `진행 상태`는 `진행 상태(레거시)`로 이름을 바꾸고 전환용 보기에서 숨긴다.
3. 기존 값을 새 단계로 확실히 옮길 수 있는 행만 변환한다.
4. 판단이 필요한 행은 단계는 유지하고 `제작 단계 확인=확인 필요`로 표시한다.
5. 전환 검증 완료 후 `제작 단계(전환용)`을 `제작 단계`로 이름을 바꾼다.

`제작 단계` 옵션은 정확히 다음을 사용한다.

- 작업 차단
- 모델링 대기
- 모델링 중
- 내부 모델 검수
- 색상 매핑
- 플레이트 구성
- 출력 대기
- 출력 중
- 후가공
- 품질 검수
- 포장 대기
- 제작 완료

고객 배송 상태나 결제 상태를 이 속성에 섞지 않는다.

#### 5.3 구조화할 상태 속성

다음 속성을 추가한다.

| 속성 | 타입 | 옵션 또는 규칙 |
|---|---|---|
| 주문 연결 | 상태 또는 선택 | 확인 필요, 확인 완료, 불일치 |
| 제작 단계 확인 | 상태 또는 선택 | 확인 필요, 확인 완료 |
| 필라멘트 매핑 상태 | 상태 또는 선택 | 미확인, 부분 완료, 완료, 불일치 |
| 플레이트 편성 상태 | 상태 또는 선택 | 미편성, 편성 중, 편성 완료 |
| 자료 연결 상태 | 상태 또는 선택 | 누락, 일부 연결, 완료 |
| 작업 상태 | 상태 또는 선택 | 대기, 진행 중, 완료, 보류 |
| 현재 문제 | 관계 | `완성·실패·재작업 사례 자료실`과 연결 |
| 최종 작업 시각 | 최종 편집 시각 | 자동 |

긴 `전환 확인 메모`에 구조화 가능한 내용을 계속 누적하지 않는다. 상태는 위 속성에 기록하고, 메모에는 사람이 읽어야 하는 이유만 남긴다.

#### 5.4 담당자 처리

1. 기존 `담당자(전환용)`이 사람 속성이면 `담당자`로 이름을 바꾼다.
2. 사람이 아닌 선택 속성이면 기존 속성을 보존하고 새 `담당자` 사람 속성을 추가한다.
3. 다음 이름이 워크스페이스 사용자와 확실히 일치할 때만 매핑한다.
   - 박신형
   - 박나혜
   - 이종무
   - 박선아
   - 황성욱
4. 제작 보조는 아직 채용 전이므로 가짜 사용자나 임의 이메일을 만들지 않는다.
5. 제작 보조 채용 전 출력·후가공·검수 기본 담당자는 박나혜다.
6. 제작 보조 채용 후 신규 작업만 새 담당자에게 배정한다. 기존 진행 건을 자동 이관하지 않는다.

#### 5.5 실무자 보기

다음 연결된 보기를 만든다. 모든 보기는 `현재 문제 있음 → 작업기한 오름차순 → 주문번호 오름차순`으로 정렬한다.

| 보기 | 필터 | 주로 보일 속성 |
|---|---|---|
| 내 작업 | 담당자=현재 사용자, 작업 상태≠완료 | 주문번호, 아이 이름, 사진, 제작 단계, 필요한 자료, 작업기한, 현재 문제 |
| 모델링 작업 | 제작 단계=모델링 대기/모델링 중/내부 모델 검수 | 주문번호, 아이 이름, 얼굴 사진, 멀티뷰, 모델링 원본, 모델링 파일, 메모 |
| 색상 매핑 | 제작 단계=색상 매핑 | 주문번호, 아이 이름, 얼굴 사진, 모델링, 부위별 색상 매핑, 사용 필라멘트 |
| 플레이트 구성 | 제작 단계=플레이트 구성 | 주문번호, 아이 이름, 사용 필라멘트, 플레이트 자료, 편성 상태 |
| 출력 진행 | 제작 단계=출력 대기/출력 중 | 주문번호, 아이 이름, 플레이트 자료, 담당자, 문제 |
| 후가공·검수 | 제작 단계=후가공/품질 검수 | 주문번호, 아이 이름, 기준 사진, 모델링, 문제, 재작업 여부 |
| 문제·보류 | 작업 상태=보류 또는 문제 존재 | 주문번호, 아이 이름, 담당자, 문제 유형, 메모, 관리자 링크 |

보기마다 전체 속성을 노출하지 않는다. 실무자가 현재 판단에 필요한 속성만 7~10개 이내로 보이게 한다.

Notion API 또는 현재 GPT 도구가 보기를 생성·수정하지 못하면 성공했다고 말하지 말고, 위 표를 그대로 `수동 보기 설정 체크리스트`로 결과에 남긴다.

#### 5.6 기존 데이터 정리

현재 확인된 기준은 다음과 같다. 실제 조회 결과와 다르면 실제 수치를 우선하되 차이를 보고한다.

- 제작 행: 약 57개
- 주문번호 입력: 약 19개
- 주문번호 확인 필요: 약 38개
- 흰색 체크가 있지만 실제 스풀 선택이 필요한 행: 약 27개

처리 규칙:

1. 주문번호가 비어 있으면 `주문 연결=확인 필요`.
2. 주문번호가 유일하고 관리자 링크가 일치하면 `주문 연결=확인 완료`.
3. 기존 색상 체크와 필라멘트 관계가 하나로 확실히 대응할 때만 관계를 연결한다.
4. `White`처럼 후보가 여러 개인 색상은 자동 연결하지 않고 `필라멘트 매핑 상태=부분 완료`.
5. 모델링 파일, 멀티뷰, 플레이트 자료 중 단계에 필요한 자료가 없으면 `자료 연결 상태=누락`.
6. `P01`~`P15` 값만 있는 행은 `플레이트 편성 상태=미편성`으로 둔다.
7. 기존 파일과 체크박스는 `기존 원본 · 체크박스 보존` 보기에서 계속 확인할 수 있게 한다.

### 6. 필라멘트 재고 트래커

기존 `F-001`~`F-014` 식별자는 유지한다. 다음 속성을 보완한다.

| 속성 | 타입 | 규칙 |
|---|---|---|
| 잔여 중량(g) | 숫자 | 스풀 포함 실측이면 메모에 표시 |
| 빈 스풀 중량(g) | 숫자 | 제조사·규격별 실제값 |
| 실사용 가능 중량(g) | 수식 | `max(잔여 중량-빈 스풀 중량, 0)` |
| 재주문 기준(g) | 숫자 | 운영자가 정한 기준 |
| 잔량 측정일 | 날짜 | 마지막 실제 측정일 |
| 실측 필요 | 수식 또는 체크박스 | 사용 중이고 측정이 오래됐거나 값 누락 시 참 |
| 재주문 필요 | 수식 또는 체크박스 | 소진 또는 실사용량≤재주문 기준 |
| 활성 여부 | 체크박스 | 신규 매핑 가능 여부 |

정합성 규칙:

1. `상태=소진`인데 남은량이 0보다 크면 `확인 필요`로 분류한다.
2. `상태=사용중`인데 잔량 측정일 또는 중량이 없으면 `실측 필요`.
3. `F-010 Bambu Ivory white PLA Matte`처럼 소진과 10%가 동시에 기록된 행은 자동 수정하지 말고 확인 목록에 올린다.
4. `재고 부족` 보기는 `재주문 필요=true`만 보이게 한다.
5. 색상명만으로 주문과 스풀을 자동 연결하지 않는다. 실제 스풀 ID가 선택돼야 완료다.

### 7. 플레이트 제작 자료실

기존 `P01`~`P15` 기록은 레거시 자료로 보존한다. 실제 출력 배치에는 별도의 고유 식별자를 사용한다.

다음 속성을 추가한다.

| 속성 | 타입 | 옵션 또는 규칙 |
|---|---|---|
| 관리자 PrintBatch ID | 텍스트 | 관리자 서버가 발급 |
| 플레이트 상태 | 상태 또는 선택 | 편성 중, 출력 대기, 출력 중, 성공, 부분 실패, 전체 실패 |
| 출력 담당자 | 사람 | 현재 박나혜, 추후 제작 보조 가능 |
| 출력 예정일 | 날짜 | 선택 |
| 출력 시작 시각 | 날짜 | API 미러 |
| 출력 종료 시각 | 날짜 | API 미러 |
| 출력 결과 | 텍스트 | 결과 요약 |
| 재출력 횟수 | 숫자 | 기본 0 |
| 실패 유형 | 다중 선택 | 접착 실패, 퍼지 문제, 필라멘트 문제, 형상 문제, 기기 문제, 기타 |
| 실제 사용량(g) | 숫자 | 선택 |
| 폐기량(g) | 숫자 | 선택 |
| 동기화 상태 | 선택 | 미연결, 정상, 전송 대기, 오류, 충돌 |

플레이트 한 개에는 여러 제작 행이 관계로 연결될 수 있다. 출력 시작과 완료는 관리자 서버가 배치 단위로 처리한다. Notion에서 직접 주문 단계를 일괄 변경하지 않는다.

### 9. API 동기화 속성

`반려동물 모델링·출력 트래커`에 다음 속성을 추가하고 기본 작업 보기에서는 숨긴다.

| 속성 | 타입 | 소유자 |
|---|---|---|
| 관리자 주문 ID | 텍스트 | 관리자 서버 |
| 관리자 작업 ID | 텍스트 | 관리자 서버 |
| 관리자 단계 | 텍스트 | 관리자 서버 |
| 관리자 담당자 ID | 텍스트 | 관리자 서버 |
| 관리자 데이터 버전 | 숫자 | 관리자 서버 |
| 동기화 상태 | 선택: 미연결, 정상, 전송 대기, 오류, 충돌 | 서버 계산 |
| 최종 동기화 시각 | 날짜 | 관리자 서버 |
| 마지막 동기화 오류 | 텍스트 | 관리자 서버 |
| 변경 요청 | 선택: 없음, 작업 시작, 작업 완료, 문제 보고, 보류 요청, 재개 요청 | 실무자 |
| 변경 요청 메모 | 텍스트 | 실무자 |
| 변경 요청 시각 | 날짜 | 실무자 또는 자동화 |
| 변경 요청 처리 결과 | 텍스트 | 관리자 서버 |

속성 소유권은 다음처럼 적용한다.

- 관리자 서버만 수정: 관리자 주문 ID, 관리자 작업 ID, 관리자 단계, 관리자 담당자 ID, 관리자 데이터 버전, 동기화 결과 필드.
- Notion 실무자 수정 가능: 멀티뷰, 모델링 파일, 부위별 색상 매핑, 사용 필라멘트 관계, 플레이트 관계, 메모, 변경 요청, 변경 요청 메모.
- Notion 실무자 수정 금지: 결제, 배송, 알림톡, 삭제, 복구, 최종 주문 상태.

`변경 요청`이 `없음`이 아닐 때만 서버가 작업 명령으로 검토한다. 단순 메모 편집이나 서버 미러 갱신은 상태 변경을 일으키지 않는다.

### 10. 변경 요청 규칙

개발 보완서의 요청자 식별·명령 식별·동시 편집 처리 규칙이 정해지기 전에는 아래 필드만으로 운영 명령 실행을 켜지 않는다. `관리자 담당자 ID`는 요청자를 증명하지 않는다. 처리 후 요청 초기화가 새 요청을 지우지 않도록 프로토콜을 검증해야 한다.

1. 실무자가 `변경 요청`과 `변경 요청 메모`를 입력한다.
2. 자동화가 가능하면 `변경 요청 시각`을 기록한다.
3. Notion 웹훅은 변경 신호만 보낸다.
4. 관리자 서버가 최신 페이지를 다시 읽는다.
5. 관리자 작업 ID와 데이터 버전을 검증한다.
6. 권한, 현재 단계, 필수 파일, 이슈를 서버에서 검증한다.
7. 성공하면 관리자 DB를 변경하고 Notion 미러를 갱신한다.
8. 처리된 요청은 `변경 요청=없음`으로 되돌리고 처리 결과를 남긴다.
9. 버전이 오래됐거나 서로 다른 변경이면 상태를 `충돌`로 두고 자동 적용하지 않는다.
10. 동일 요청이 여러 번 전달돼도 한 번만 처리한다.

### 12. 알림톡 관련 표시

Notion에서 알림톡을 직접 발송하지 않는다. 필요하면 다음 읽기 전용 미러만 둔다.

- 최근 알림 이벤트
- 최근 알림 발송 시각
- 최근 알림 결과
- 알림 실패 여부

제작 단계 롤백, 삭제, 배송 상태 변경은 관리자 페이지에서만 실행한다. 이미 발송된 알림톡이 있는 단계에서 이전 단계로 돌아갈 때 관리자 페이지가 발송 이력을 보여주고 재안내 필요 여부를 확인한다.

### 13. 변경 후 검증

수정 후 반드시 다시 조회해 다음을 검증한다.

1. 기존 4개 데이터베이스가 모두 존재한다.
2. 기존 행 수가 줄지 않았다.
3. 기존 파일과 관계가 사라지지 않았다.
4. 주문번호 없는 행에 가짜 번호가 생성되지 않았다.
5. 레거시 진행 상태와 체크박스가 보존 보기에서 확인된다.
6. 실무자 보기에 보호자명, 전화번호, 주소, 결제 정보가 없다.
7. 동기화 속성이 작업 보기에서는 숨겨져 있다.
8. 상태 옵션명이 지시와 일치한다.
9. 필라멘트 관계가 불확실한 행은 완료 처리되지 않았다.
10. `P01`~`P15`가 실제 PrintBatch ID로 오인되지 않았다.

### 14. 최종 보고 형식

최종 답변은 다음 순서로 작성한다.

1. 접근한 워크스페이스명과 대상 페이지
2. 변경 전 스냅샷
3. 실제 변경한 속성·보기·SOP
4. 데이터베이스 ID와 데이터 소스 ID 표
5. API 연동에 사용할 속성 ID·이름·타입 표
6. 자동으로 정리한 행 수
7. 사람 확인이 필요한 행 목록과 사유

9. 변경 후 검증 결과
10. 관리자 서버 개발자에게 전달할 연결 정보

성공하지 않은 작업을 성공했다고 표현하지 않는다. 페이지나 보기 수정 권한이 없으면 정확히 어느 단계에서 막혔는지 기록한다.
