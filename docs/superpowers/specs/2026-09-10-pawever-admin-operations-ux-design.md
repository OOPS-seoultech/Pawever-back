## 1. 한 문장 목표

모든 주문을 하나의 운영 시스템에서 관리하되, 실무자는 자신이 지금 처리할 일만 보고 정상 건을 최소 동작으로 끝내고, 관리자는 병목·예외·기한·작업 책임자를 한곳에서 판단하고 안전하게 수정할 수 있어야 한다.

## 2. 확정된 운영 결정

1. 관리자 DB가 주문·작업·발송·알림 이력의 유일한 원본이다.
2. `한 테이블`은 하나의 물리 SQL 테이블이 아니라, 정규화된 데이터를 합쳐 보여주는 하나의 운영 목록을 뜻한다.
3. 고객 원본 사진과 제작 파일은 기존 비공개 AWS S3에 저장한다. DB에는 객체 키와 메타데이터만 저장한다.
4. Notion은 원본 주문 관리 시스템으로 사용하지 않는다. 필요한 경우 필라멘트 목록과 읽기 전용 요약만 가볍게 연결한다.
5. 계좌이체는 관리자가 은행 앱 또는 거래내역과 직접 대조한 뒤 어드민에서 확인한다. 은행 API는 이번 범위에 포함하지 않는다.
6. 제작·발송 목표는 입금 확인 후 7영업일 이내지만, 초기에는 SLA 판정을 `OFF`로 운영한다.
7. SLA는 관리자만 전역 설정에서 `ON/OFF`할 수 있다.
8. 현재 출력·후가공·1차 검수 담당자는 박나혜다. 제작 보조 인력을 채용하면 같은 역할의 신규 작업부터 바로 이관할 수 있어야 한다.
9. 제작 보조는 한 주문당 한 명만 배정하며 검수 통과 주문당 3,000원을 정산한다. 백업 작업자는 결근·과부하 때만 재배정한다.
10. 고객에게 모델링 이미지를 매번 승인받지 않는다. 내부 모델 검수 후 제작 시작 알림톡을 보내고 출력한다.
11. 명백한 형상·색상·후가공 불량만 무료 1회 재제작 대상으로 한다.
12. 준등기는 우체국이 내보낸 6개 배송 필드와 13자리 준등기번호가 포함된 결과 데이터를 돌려준다고 가정한다.
13. 주문 삭제는 관리자 전용 소프트 삭제다. 30일 동안 휴지통에서 복구할 수 있고 이후 영구 파기한다.
14. 상태를 이전 단계로 되돌릴 때 이미 발송된 알림톡이 있으면, 관리자에게 그 발송 이력을 모달로 명확히 경고한다.
15. 역할은 기본 권한 묶음으로 사용하고, 소유 관리자는 사람별 데이터 노출과 행동 권한을 ON/OFF할 수 있다.
16. 직접 수령 장소는 `상상관`과 `다빈치관` 중 하나로 저장하고 장소별 수령 대기 목록을 제공한다.
17. 배송 주문을 여러 건 선택해 포장 완료하면 우체국 전달용 무헤더 XLSX를 즉시 생성하고, 선택 주문을 우체국 결과 대기 단계로 이동한다.
18. 담당자는 관리자가 이메일로 초대한 뒤 본인이 일회용 링크에서 비밀번호를 설정하고 이메일을 아이디로 로그인한다.

## 3. 설계 원칙

### 3.1 MECE 원칙

결제 상태, 제작 단계, 배송 상태, 주문 종결 상태, 문제 상태를 하나의 거대한 상태값으로 섞지 않는다. 각각 독립된 축으로 관리한다.

- 한 주문은 각 상태 축에서 정확히 하나의 값만 가진다.
- 문제는 기본 진행 상태를 대체하지 않고 별도 이슈로 기록한다.
- 목록의 업무 뷰는 상태값을 저장하지 않고 여러 상태 축에서 계산한다.
- 주문은 정상 업무 뷰 중 정확히 한 곳에 포함된다.
- `문제 있음`은 중첩 가능한 보조 필터이므로 정상 업무 뷰의 건수와 별도로 표시한다.

### 3.2 최소 동작 원칙

- 정상 건은 목록에서 바로 처리한다.
- 상세 화면은 판단, 수정, 예외 처리에만 사용한다.
- 상태 이름보다 실제 행동을 노출한다. 예: `상태 변경`이 아니라 `입금 확인`, `모델링 완료`, `준등기 결과 가져오기`.
- 한 작업을 완료하면 다음 담당자와 다음 작업을 시스템이 자동 생성한다.
- 처리 완료 후 같은 업무 뷰의 다음 주문을 자동 선택한다.
- 같은 플레이트에 포함된 주문은 출력 시작·완료를 플레이트 단위로 한 번만 처리한다.

### 3.3 안전 원칙

- 파괴적 작업은 확인, 사유, 감사 로그, 가능한 경우 복구를 제공한다.
- 알림톡과 감사 로그는 수정하거나 삭제하지 않는다.
- 되돌리기는 기존 이력을 삭제하는 것이 아니라 새 반대 이벤트를 추가한다.
- 모든 변경 API는 중복 요청에 안전해야 한다.
- 역할별 개인정보 최소 노출은 프론트가 아니라 서버에서 강제한다.

## 5. 사용자와 권한

### 5.1 권한 모델

`systemRole`은 기본 권한 묶음, `workRole`은 제작 업무 배정 기준, `accountPermission`은 사람별 최종 허용값이다. 실제 접근 허용 여부는 서버가 세 값을 합쳐 계산한다.

#### systemRole

- `OWNER`: 계정·권한 설정을 포함한 전체 운영. 초기 소유자는 이종무 한 명이다.
- `ADMIN`: 주문·결제·배송·삭제·복구·운영 설정. 다른 사람의 OWNER 권한은 변경할 수 없다.
- `PRODUCTION`: 배정된 제작 정보와 파일만 접근
- `MARKETING`: 집계 데이터와 마케팅 동의 고객의 승인된 내보내기만 접근
- `SUPPORT`: 시스템 상태·실패 로그 접근, 평문 개인정보는 기본 차단

#### workRole

- `MODELING`
- `DESIGN_QC`
- `PRINT_FINISHING`
- `PACKING_SHIPPING`

사람 이름을 코드에 하드코딩하지 않는다. 계정에 역할을 배정한다.

### 5.2 초기 계정 배정

| 구성원 | systemRole | workRole | 초기 책임 |
|---|---|---|---|
| 이종무 | OWNER | PACKING_SHIPPING | 입금 확인, 전체 관리, 권한 관리, 포장, 우체국 전달, 준등기 결과 반영 |
| 박신형 | PRODUCTION | MODELING | 사진 확인, 4면도, 3D 모델링, 모델러 자체 검수 |
| 박나혜 | PRODUCTION | DESIGN_QC + PRINT_FINISHING | 내부 모델 검수, 색상 매핑, 플레이트 구성, 출력, 후가공, 1차 검수 |
| 제작 보조 미정 | PRODUCTION | PRINT_FINISHING | 채용 후 신규 출력·후가공·1차 검수 작업 이관 |
| 박선아 | MARKETING | 없음 | 채널별 성과와 동의 고객 대상 마케팅 |
| 황성욱 | SUPPORT | 없음 | 백엔드·프론트엔드·인프라 유지보수 |

#### 계산 규칙

1. 모든 권한은 기본 거부다.
2. 역할 기본 권한을 불러온다.
3. 계정별 `ALLOW` 또는 `DENY` override를 적용한다.
4. `DENY`가 `ALLOW`보다 우선한다.
5. 데이터 행 범위도 별도로 검사한다. 사진 보기 권한이 ON이어도 배정되지 않은 주문은 볼 수 없다.
6. OWNER만 `MANAGE_ACCOUNT_PERMISSIONS`를 다른 계정에 부여하거나 회수할 수 있다.
7. 마지막 활성 OWNER의 계정 관리·권한 관리·복구 권한은 끌 수 없다.
8. 본인은 자신의 권한을 변경할 수 없다.
9. 개인정보 권한을 켤 때 목적과 사유를 기록한다. 선택적으로 만료 시각을 지정할 수 있다.
10. 권한 변경은 다음 요청부터 즉시 적용한다. 기존 로그인 토큰의 오래된 권한값을 신뢰하지 않는다.
11. 누가 누구의 어떤 권한을 언제 켜거나 껐는지 감사 로그에 남긴다.
12. 관리자 ON은 `ALLOW`, OFF는 `DENY` override를 만든다. `역할 기본값으로 되돌리기`는 override를 삭제한다.
13. 역할을 바꿔도 기존 사람별 override를 자동 삭제하지 않고 변경 전 최종 권한과 변경 후 최종 권한을 비교해 보여준다.

주문 행 범위는 `배정 주문만`이 기본이다. `VIEW_ROLE_QUEUE`가 ON이면 같은 workRole 대기열까지, `VIEW_ALL_ORDERS`가 ON이면 전체 주문 행까지 확장한다. 행 범위가 넓어져도 보호자·연락처·주소·사진은 각 데이터 권한이 OFF면 내려주지 않는다.

행동 권한의 필수 데이터 권한:

| 행동 권한 | 함께 필요한 데이터 권한 |
|---|---|
| `CONFIRM_PAYMENT` | VIEW_ORDER_BASIC, VIEW_PAYMENT |
| `COMPLETE_MODELING` | VIEW_ORDER_BASIC, VIEW_CUSTOMER_PHOTOS, VIEW_PRODUCTION_FILES |
| `REVIEW_MODEL` | VIEW_ORDER_BASIC, VIEW_CUSTOMER_PHOTOS, VIEW_PRODUCTION_FILES |
| `MANAGE_PRINT_BATCH` | VIEW_ORDER_BASIC, VIEW_PRODUCTION_FILES, VIEW_FILAMENT |
| `PACK_AND_EXPORT_SHIPMENTS` | VIEW_ORDER_BASIC, VIEW_CUSTOMER_IDENTITY, VIEW_CUSTOMER_CONTACT, VIEW_CUSTOMER_ADDRESS, VIEW_SHIPMENT |
| `IMPORT_SHIPMENT_RESULTS` | VIEW_ORDER_BASIC, VIEW_SHIPMENT |
| `COMPLETE_PICKUP` | VIEW_ORDER_BASIC, VIEW_CUSTOMER_IDENTITY, VIEW_SHIPMENT |

행동 권한을 켤 때 필수 데이터 권한이 꺼져 있으면 함께 켜질 권한을 먼저 알려주고 한 번에 적용한다. 필수 데이터 권한을 끄려 할 때는 영향을 받는 행동 권한을 함께 끌 것인지 확인한다. 모순된 권한 조합은 저장하지 않는다.

역할 변경은 기본값 묶음을 바꾸는 행동이고, 사람별 ON/OFF는 예외를 조정하는 행동이다. 프론트가 메뉴를 숨기는 것만으로 권한을 구현하지 않는다.

### 5.5 이메일 초대와 최초 로그인

계정 상태:

- `INVITED`: 초대 메일 발송, 비밀번호 미설정
- `ACTIVE`: 로그인 가능
- `SUSPENDED`: 일시 정지, 재활성화 가능
- `DEACTIVATED`: 업무 종료, 로그인 불가

초대 흐름:

1. OWNER 또는 `MANAGE_ACCOUNTS` 권한이 있는 관리자가 담당자의 이메일을 입력한다.
2. systemRole, workRole, 역할 기본 권한과 사람별 override를 확인한다.
3. 서버는 이메일을 소문자·공백 제거 형태로 정규화하고 중복 계정을 차단한다.
4. 서버는 1회용 초대 토큰을 만들고 해시만 DB에 저장한다.
5. 초대 링크 유효기간은 24시간이다. 만료되면 관리자가 다시 발송할 수 있다.
6. 이메일 주인이 링크로 접속해 비밀번호를 설정한다.
7. 토큰은 한 번 사용하면 즉시 폐기되고 계정은 ACTIVE가 된다.
8. 이후 이메일과 비밀번호로 로그인한다.
9. 비밀번호는 기존 프로젝트의 검증된 password encoder로 단방향 해시한다.
10. 권한 변경·계정 정지·비활성화 시 기존 세션을 즉시 무효화한다.
11. 관리자는 담당자의 비밀번호를 보거나 대신 지정하지 않는다.
12. 비밀번호 분실 시 같은 이메일로 30분 유효 1회용 재설정 링크를 보내고, 사용 후 모든 기존 세션을 무효화한다.

초대 메일 발송이 실패하면 계정은 INVITED로 유지하고 관리자에게 재발송 행동과 실패 원인을 제공한다. 초대 링크 자체는 애플리케이션 로그에 남기지 않는다.

초대 요청 예시:

```json
{
  "email": "worker@example.com",
  "systemRole": "PRODUCTION",
  "workRoles": ["PRINT_FINISHING"],
  "permissionOverrides": {
    "VIEW_CUSTOMER_PHOTOS": "ALLOW",
    "VIEW_CUSTOMER_ADDRESS": "DENY"
  }
}
```

## 6. 도메인 상태 모델

현재 `GoodsOrderStatus` 하나에 결제·제작·배송이 섞여 있다. 아래 상태 축으로 분리하고, 기존 값을 데이터 마이그레이션한 뒤 이중 기록 없이 새 모델만 사용한다.

### 6.1 주문 종결 상태 `orderStatus`

| 값 | 의미 |
|---|---|
| `ACTIVE` | 처리 중인 정상 주문 |
| `COMPLETED` | 준등기 배달 완료 또는 현장 수령 완료 |
| `CANCELED` | 운영자 또는 고객 요청으로 취소 완료 |
| `EXPIRED` | 미입금 기한 만료 |

소프트 삭제는 업무 상태가 아니므로 `deletedAt`으로 따로 관리한다.

### 6.2 결제 상태 `paymentStatus`

| 값 | 의미 |
|---|---|
| `PENDING` | 계좌 입금 대기 |
| `CONFIRMED` | 관리자가 입금 확인 또는 외부 채널 선결제 확인 |
| `NOT_REQUIRED` | 체험단 등 상품 대금이 없는 주문 |
| `REFUND_PENDING` | 취소됐지만 계좌 환불 확인 전 |
| `REFUNDED` | 환불 완료 |
| `FAILED` | 결제 처리 실패 |
| `EXPIRED` | 입금 기한 만료 |

### 6.3 제작 단계 `productionStage`

| 순서 | 값 | 기본 담당 역할 | 완료 조건 |
|---:|---|---|---|
| 0 | `BLOCKED` | 없음 | 입금 미확인 또는 필수 자료 부족 |
| 1 | `MODELING_QUEUE` | MODELING | 모델링 담당자 배정 |
| 2 | `MODELING` | MODELING | 4면도·3D 모델 파일 업로드 및 자체 체크 완료 |
| 3 | `MODEL_REVIEW` | DESIGN_QC | 닮음·형상·출력 가능성 내부 검수 통과 |
| 4 | `COLOR_MAPPING` | DESIGN_QC | 사용 필라멘트와 부위별 색상 매핑 완료 |
| 5 | `PLATE_PREPARATION` | DESIGN_QC | PrintBatch 배정 및 3MF/G-code 등록 |
| 6 | `PRINT_QUEUE` | PRINT_FINISHING | 출력 담당자·프린터 준비 |
| 7 | `PRINTING` | PRINT_FINISHING | 플레이트 출력 종료 및 개별 결과 확인 |
| 8 | `POST_PROCESSING` | PRINT_FINISHING | 서포터 제거·레진 경화 등 완료 |
| 9 | `QC` | PRINT_FINISHING | 체크리스트 통과 또는 재작업 판정 |
| 10 | `PACKING` | PACKING_SHIPPING | 개별 포장 완료 |
| 11 | `COMPLETE` | 없음 | 배송 또는 현장 수령 준비 완료 |

### 6.4 배송 상태 `shipmentStatus`

기존 PICKUP 주문은 장소를 저장하지 않았다. 아래 장소 필수 규칙의 과거 주문 적용과 신규 허용 채널은 개발 보완서 Q1 답변 후 확정한다. 기존 행에 임의 건물을 채우지 않는다.

| 값 | 의미 |
|---|---|
| `NOT_READY` | 제작 또는 포장 미완료 |
| `AWAITING_POST_OFFICE_RESULT` | 포장 완료와 우체국 XLSX 생성이 끝나 결과 데이터를 기다림 |
| `ACCEPTED` | 준등기번호가 반영되어 우체국 접수가 확인됨 |
| `DELIVERED` | 우편함 배달 완료가 확인됨 |
| `READY_FOR_PICKUP` | 선택한 장소에서 직접 수령 가능 |
| `PICKED_UP` | 현장 수령 완료 |
| `EXCEPTION` | 준등기번호 오류, 반송, 분실 등 확인 필요 |

직접 수령 장소는 배송 상태에 넣지 않고 `pickupLocation`으로 분리한다.

| pickupLocation | 고객 표시 | 의미 |
|---|---|---|
| `SANGSANG_HALL` | 상상관 | 상상관 직접 수령 |
| `DAVINCI_HALL` | 다빈치관 | 다빈치관 직접 수령 |

규칙:

- `deliveryMethod=PICKUP`이면 `pickupLocation`은 필수다.
- `deliveryMethod=SHIPPING`이면 `pickupLocation`은 null이어야 한다.
- 직접 수령 장소 변경은 PICKED_UP 전까지만 가능하다.
- 장소를 바꾸면 변경자·변경 전후 장소·변경 시각을 감사 로그에 남긴다.
- 상상관과 다빈치관 수령 대기 목록을 각각 조회할 수 있어야 한다.

### 6.5 이슈 `issue`

이슈는 주문의 진행 단계를 바꾸지 않는다. 한 주문에 여러 이슈가 동시에 존재할 수 있다.

| 코드 | 의미 | 기본 책임자 |
|---|---|---|
| `PHOTO_INSUFFICIENT` | 제작에 필요한 사진 부족 | ADMIN |
| `PAYMENT_MISMATCH` | 입금자명 또는 금액 불일치 | ADMIN |
| `UNASSIGNED` | 현재 단계 담당자 없음 | ADMIN |
| `ARTIFACT_MISSING` | 단계 완료 필수 파일 없음 | 현재 담당자 |
| `SLA_AT_RISK` | SLA ON 주문의 마감 임박 | 현재 담당자·ADMIN |
| `SLA_OVERDUE` | SLA ON 주문의 기한 초과 | ADMIN |
| `PRINT_FAILED` | 출력 실패 | PRINT_FINISHING |
| `QC_FAILED` | 검수 실패 | DESIGN_QC 또는 PRINT_FINISHING |
| `REMAKE_REQUIRED` | 무료 재제작 승인 | ADMIN |
| `SHIPMENT_IMPORT_ERROR` | 준등기 결과 매칭 실패 | ADMIN |
| `NOTIFICATION_FAILED` | 알림톡 발송 실패 | ADMIN |
| `CUSTOMER_CONTACT_REQUIRED` | 롤백 등으로 별도 고객 안내 필요 | ADMIN |

이슈 상태는 `OPEN`, `RESOLVED`, `DISMISSED` 중 하나다. 해결 시 해결자, 해결 시각, 해결 메모를 필수로 기록한다.

### 6.6 기존 상태 마이그레이션

아래 표는 원문 보존용이다. `IN_PRODUCTION`의 불명확한 단계, `SHIPPED`의 완료 판정, `CANCELED`의 환불 근거처럼 문서 간 충돌하거나 근거가 없는 값은 이 표만으로 자동 적용하지 않는다. 실행 규칙은 개발 보완서의 상태 이전 항목과 Q2를 따른다. 확인되지 않은 행을 자동 배정하거나 고객에게 알리지 않는다.

| 기존 GoodsOrderStatus | orderStatus | paymentStatus | productionStage | shipmentStatus |
|---|---|---|---|---|
| `PAYMENT_PENDING` | ACTIVE | PENDING | BLOCKED | NOT_READY |
| `PAYMENT_COMPLETED` | ACTIVE | CONFIRMED | MODELING_QUEUE | NOT_READY |
| `IN_PRODUCTION` | ACTIVE | CONFIRMED 또는 NOT_REQUIRED | 현재 자료로 추론, 불가하면 MODELING_QUEUE | NOT_READY |
| `SHIPPED` | ACTIVE | CONFIRMED 또는 NOT_REQUIRED | COMPLETE | ACCEPTED |
| `PICKED_UP` | COMPLETED | CONFIRMED 또는 NOT_REQUIRED | COMPLETE | PICKED_UP |
| `PAYMENT_EXPIRED` | EXPIRED | EXPIRED | BLOCKED | NOT_READY |
| `PAYMENT_FAILED` | CANCELED | FAILED | BLOCKED | NOT_READY |
| `CANCELED` | CANCELED | REFUNDED 또는 NOT_REQUIRED | 현재값 유지 | NOT_READY |
| `CANCEL_FAILED` | ACTIVE | REFUND_PENDING | 현재값 유지 | NOT_READY + 이슈 생성 |
| `LEGACY_FREE` | ACTIVE | NOT_REQUIRED | MODELING_QUEUE | NOT_READY |

마이그레이션이 끝나면 기존 복합 상태 필드와 프론트의 중복 전이표를 제거한다.

## 7. 업무 뷰 계산 규칙

업무 뷰는 저장값이 아니라 서버 쿼리로 계산한다.

| 업무 뷰 | 포함 조건 | 기본 사용자 |
|---|---|---|
| `PAYMENT_CHECK` | ACTIVE + paymentStatus=PENDING | 이종무 |
| `PRODUCTION_QUEUE` | ACTIVE + 결제 허용 + productionStage=MODELING_QUEUE | 박신형 |
| `IN_PRODUCTION` | ACTIVE + productionStage=MODELING~QC | 제작팀 |
| `PACKING_SHIPPING` | ACTIVE + productionStage=PACKING 또는 COMPLETE + 배송 미완료 | 이종무 |
| `DONE` | orderStatus=COMPLETED | 관리자 |
| `CANCELED_EXPIRED` | orderStatus=CANCELED 또는 EXPIRED | 관리자 |
| `PROBLEM` | OPEN 이슈가 하나 이상 | 관리자·해당 담당자 |
| `TRASH` | deletedAt != null | 관리자만 |

`PROBLEM`은 중첩 뷰다. 운영 합계는 정상 업무 뷰끼리만 합산한다.

목록 정렬 기본값:

1. 작업을 막는 OPEN 이슈
2. SLA 초과
3. SLA 임박
4. 오래 대기한 주문
5. 최신 주문

## 8. 전체 운영 프로세스

### 8.1 신청과 입금

1. 주문 접수 시 주문번호를 생성한다.
2. 채널, 외부 주문번호, 고객 정보, 반려동물 정보, 선택 옵션, 예상 입금자명, 결제 금액, 사진 객체 키를 저장한다.
3. 직접 수령 주문은 상상관 또는 다빈치관 중 하나를 반드시 선택한다. 배송 주문은 직접 수령 장소를 저장하지 않는다.
4. 랜딩 계좌이체 주문은 `paymentStatus=PENDING`, `productionStage=BLOCKED`로 생성한다.
5. 입금 요청 알림톡을 한 번만 발송한다.
6. 접수 후 48시간 안에 입금되지 않으면 `paymentStatus=EXPIRED`, `orderStatus=EXPIRED`로 이동하고 고객 사진을 파기 대상으로 등록한다.
7. 관리자가 외부 은행 화면에서 입금자명과 금액을 확인한다.
8. 정상 건은 `입금 확인` 한 동작으로 처리한다.
9. 서버는 확인자와 확인 시각을 기록하고 `paymentStatus=CONFIRMED`, `productionStage=MODELING_QUEUE`로 이동한다.
10. 모델링 담당 작업을 자동 생성하고 기본 담당자 박신형에게 배정한다.
11. 이름 또는 금액이 다르면 상태를 이동하지 않고 `PAYMENT_MISMATCH` 이슈를 생성한다.

### 8.2 모델링과 내부 검수

1. 박신형은 자신의 `MODELING_QUEUE`만 본다.
2. 사진은 상세 진입 즉시 짧은 만료 링크로 보이고, 전체 다운로드는 한 번에 ZIP으로 제공한다.
3. 4면도와 3D 모델 파일을 같은 작업에 업로드한다.
4. 필수 파일과 자체 체크를 완료하면 `모델링 완료`를 실행한다.
5. 주문은 `MODEL_REVIEW`로 이동하고 박나혜에게 자동 배정된다.
6. 박나혜는 고객 사진, 4면도, 모델을 같은 주문 컨텍스트에서 확인한다.
7. 통과하면 `COLOR_MAPPING`으로 이동한다.
8. 실패하면 `QC_FAILED` 이슈와 수정 메모를 남기고 `MODELING`으로 되돌린다.
9. 모델 내부 검수 통과 시 승인된 신규 `제작 시작 안내` 알림톡을 한 번 발송한다.

고객의 모델 이미지 사전 승인 단계는 두지 않는다.

### 8.3 색상과 플레이트 구성

1. 박나혜가 반려동물 부위별 필라멘트를 매핑한다.
2. 시스템은 같은 재료 조합과 마감 조건을 가진 주문을 플레이트 후보로 제안할 수 있다.
3. 실제 묶음 결정은 박나혜가 한다.
4. `PrintBatch`에 여러 주문을 연결하고 3MF/G-code를 등록한다.
5. 플레이트가 확정되면 연결 주문을 모두 `PRINT_QUEUE`로 이동한다.
6. 현재는 `PRINT_FINISHING` 기본 담당자를 박나혜로 지정한다.
7. 제작 보조 계정이 활성화되면 관리자가 `신규 작업 기본 담당자`를 제작 보조로 변경한다. 기존 진행 건은 자동 이관하지 않는다.

### 8.4 출력·후가공·검수

1. 출력 시작은 주문별이 아니라 `PrintBatch` 단위로 처리한다.
2. 한 번의 시작 동작으로 배치와 연결 주문 모두 `PRINTING`이 된다.
3. 중간 확인 기록은 배치에 남긴다. 이상이 있는 주문만 개별 이슈를 만든다.
4. 출력 완료 후 주문별로 성공·실패를 판정한다.
5. 성공 주문은 `POST_PROCESSING`, 실패 주문은 `PRINT_FAILED` 이슈와 재출력 대기로 보낸다.
6. 담당자는 서포터 제거, 레진 경화, 표면 상태 확인을 완료한다.
7. 1차 검수 체크리스트를 통과하면 `PACKING`으로 이동한다.
8. 검수 통과 시점에 담당자의 건당 3,000원 정산 항목을 생성한다. 같은 주문에 중복 생성할 수 없다.
9. 재출력·재작업은 새 시도 번호를 만들되 최초 정산은 한 번만 인정한다. 관리자가 추가 정산을 승인한 경우만 예외 항목을 추가한다.

초기 박나혜 운영 중에도 동일한 배정·작업·정산 구조를 사용하되 실제 지급액은 설정으로 비활성화할 수 있다.

### 8.5 포장과 준등기 발송

1. 포장 담당자가 배송할 주문의 보호자·반려동물 행을 체크박스로 여러 개 선택한다.
2. `선택 주문 포장 완료 및 우체국 파일 받기`를 한 번 실행한다.
3. 서버는 선택 주문 전체를 먼저 검증한다. 한 건이라도 배송 정보가 잘못되면 XLSX를 만들거나 상태를 이동하지 않고 수정할 주문을 반환한다.
4. 검증이 통과하면 주문별 포장 완료를 기록한다.
5. `ShipmentExportBatch`를 만들고 포함 주문, 엑셀 행 번호, 내보낸 값의 스냅샷을 저장한다.
6. 헤더가 없는 6열 XLSX를 생성해 바로 다운로드한다.
7. 파일 생성이 성공한 경우에만 선택 주문을 `productionStage=COMPLETE`, `shipmentStatus=AWAITING_POST_OFFICE_RESULT`로 일괄 이동한다.
8. 현장 수령 주문은 이 동작에서 제외하고 별도 직접 수령 흐름으로 보낸다.
9. 포장 담당자가 상품과 파일을 우체국에 전달한다. 추가 상태 변경 동작은 요구하지 않는다.
10. 우체국 결과 파일을 가져오면 내보낸 배치 스냅샷과 비교한다.
11. 정상 매칭된 행만 `ACCEPTED`로 이동하고 상품 발송 알림톡을 보낸다.
12. 누락, 추가, 중복, 정보 변경, 준등기번호 오류는 비교 결과 모달에 분리해 표시한다.
13. 관리자는 오류 행을 제외하거나, 주문과 연결하거나, 배송 정보를 수정한 뒤 해당 행만 재처리할 수 있다.
14. 오류 처리에서 `삭제`를 선택하면 주문을 영구 삭제하지 않고 관리자 전용 휴지통으로 이동한다.
15. 이미 정상 반영된 행은 오류 행을 수정할 때 되돌리지 않는다.
16. 같은 결과 파일을 다시 가져와도 알림톡과 상태 전이는 중복 실행되지 않는다.
17. 배달 완료가 확인되면 `DELIVERED`, `orderStatus=COMPLETED`로 변경하고 배송도착 알림톡을 보낸다.

### 8.6 현장 수령

1. 신청 또는 관리자 수정 시 상상관과 다빈치관 중 하나를 선택한다.
2. 포장 담당자가 직접 수령 주문을 여러 건 선택해 포장 완료할 수 있다.
3. 포장 완료 시 `productionStage=COMPLETE`, `shipmentStatus=READY_FOR_PICKUP`으로 이동한다.
4. 장소별 목록에서 보호자·반려동물을 확인한다.
5. 직접 전달한 주문만 `수령 완료` 처리한다.
6. `shipmentStatus=PICKED_UP`, `orderStatus=COMPLETED`로 이동한다.
7. 송장이나 준등기번호는 요구하지 않는다.
8. 상상관 주문과 다빈치관 주문을 한 목록에서 섞어 일괄 완료하지 않는다.

### 8.7 재제작

무료 1회 재제작 가능 사유:

- 출력 파손
- 심한 색상 누락
- 눈·코 등 핵심 부위 후가공 불량
- 좌우·앞뒤 형상이 명백하게 잘못됨
- 내부 기준상 반려동물의 핵심 특징이 현저히 누락됨

처리 규칙:

1. 증빙 사진, 사유 코드, 책임 단계, 발견 단계, 승인자를 기록한다.
2. `REMAKE_REQUIRED` 이슈를 생성하고 `remakeAttempt=1`을 부여한다.
3. 원래 주문번호를 유지하고 별도 제작 시도를 생성한다.
4. 재제작 시작 단계는 관리자가 선택한다. 모델 문제면 MODELING, 출력 문제면 PRINT_QUEUE, 후가공 문제면 POST_PROCESSING이다.
5. 추가 재료비, 작업비, 발송비를 원 주문의 추가 원가로 기록한다.
6. 두 번째 무료 재제작은 관리자 명시 승인 없이는 생성할 수 없다.

## 9. 역할별 UX 요구사항

이 절은 화면 모양이 아니라 사용 흐름과 동작 기준을 정의한다.

### 9.1 공통

- 로그인 후 기본 진입점은 `내 작업`이다.
- 서버가 현재 역할, 담당자, 선행 작업 완료 여부에 맞는 주문만 반환한다.
- 각 행은 `주문 식별`, `필수 자료 준비 여부`, `기한`, `현재 단계`, `다음 행동`을 제공한다.
- 정상 건의 기본 행동은 행에서 실행한다.
- 행동 실행 중 중복 클릭을 막고 원래 버튼 문구를 유지한 채 처리 중 상태를 알린다.
- 성공 결과는 읽기 가능한 상태 메시지로 알리고 다음 주문에 초점을 이동한다.
- 실패 시 문제가 발생한 주문과 해결 방법을 같은 위치에서 알려준다.
- 모든 작업은 마우스 없이도 완료 가능해야 한다.
- 모달은 열릴 때 제목 또는 첫 필수 입력으로 초점을 이동하고 닫힐 때 실행 버튼으로 초점을 돌려준다.

### 9.2 관리자 이종무

관리자가 답해야 할 질문:

1. 지금 즉시 결정해야 하는 주문은 무엇인가?
2. 어느 단계에 작업이 쌓였는가?
3. 누가 과부하이거나 작업이 없는가?
4. 입금·파일·배송·알림 누락이 있는가?
5. 오늘 우체국에 전달할 주문과 결과 미반영 주문은 무엇인가?
6. 재작업과 추가 원가가 얼마나 발생했는가?

관리자 기본 행동:

- 입금 확인
- 입금 불일치 표시·해결
- 담당자 변경
- 이전 단계로 되돌리기
- 다른 단계로 강제 이동
- 주문 취소·환불 상태 기록
- 우체국 엑셀 내보내기
- 준등기 결과 가져오기·오류 수정
- 현장 수령 완료
- 상상관·다빈치관 수령 장소 변경
- 재제작 승인
- 휴지통 이동·복구·영구 파기
- SLA ON/OFF 및 신규 기본 담당자 변경
- 이메일 담당자 초대·비활성화·재활성화
- 사람별 정보 노출·행동 권한 ON/OFF

관리자 요약 수치는 다음 세 그룹으로 분리한다.

| 그룹 | 지표 |
|---|---|
| 즉시 결정 | 결제 불일치, 미배정, 준등기 오류, 알림 실패, 재제작 승인 대기 |
| 처리량·병목 | 단계별 현재 건수, 최장 대기 시간, 담당자별 활성 작업 수, 플레이트 수 |
| 결과·품질 | 완료, 기한 초과, 출력 실패율, 재제작률, 추가 원가, 배달 완료 |

### 9.3 모델링 담당 박신형

필요 정보:

- 주문번호, 반려동물 이름, 상품 옵션, 키링 여부
- 원본 사진 3~5장
- 모델링 수정 메모와 이전 실패 사유
- 목표 완료일과 우선순위

정상 흐름:

1. 다음 주문 시작
2. 사진 전체 다운로드
3. 4면도·3D 모델 파일 업로드
4. 자체 검수 항목 확인
5. 모델링 완료
6. 다음 주문 자동 선택

보호자 이름, 전화, 주소, 결제 정보는 제공하지 않는다.

### 9.4 디자인·내부 검수 담당 박나혜

필요 정보:

- 고객 사진, 4면도, 3D 모델
- 모델러 자체 검수 결과
- 보유 필라멘트, 잔량, 색상, 구입처
- 같은 재료 조합의 플레이트 후보

정상 흐름:

1. 모델 승인 또는 수정 요청
2. 부위별 필라멘트 매핑
3. 플레이트 후보 선택·조정
4. 3MF/G-code 등록
5. 플레이트 확정

수정 요청 시 자유 메모만 받지 않고 사유 코드를 먼저 선택한다. 예: 얼굴 형태, 귀, 꼬리, 자세, 하단 커팅, 출력 가능성, 색상 분리.

### 9.5 출력·후가공 담당 박나혜 또는 제작 보조

필요 정보:

- PrintBatch 번호, 프린터, 포함 주문, 필라멘트 슬롯, 3MF/G-code
- 주문별 사진과 색상 매핑
- 출력·후가공·검수 체크리스트

정상 흐름:

1. 플레이트 파일 내려받기
2. 출력 시작
3. 필요 시 중간 확인 기록
4. 플레이트 출력 완료
5. 주문별 실패 여부만 분리
6. 후가공 완료
7. 1차 검수 통과

정상 플레이트는 시작과 완료를 각 한 번만 처리한다. 개별 주문을 매번 열게 하지 않는다.

### 9.6 마케팅 담당 박선아

제공 정보:

- 일·주·월 채널별 신청, 결제 확인, 취소, 완료, 매출 집계
- 마케팅 동의율
- 캠페인·유입 파라미터 집계
- 관리자 승인 후 생성된 마케팅 동의 고객 내보내기

제작 파일, 원본 사진, 주소, 비동의 고객 연락처는 제공하지 않는다.

### 9.7 개발 담당 황성욱

제공 정보:

- API 실패율, 배치 작업 실패, S3 오류, 알림 제공자 오류, 엑셀 파싱 오류
- 주문번호, 이벤트 ID, 오류 코드, 발생 시각

평문 개인정보와 사진은 기본 제공하지 않는다. 장애 조사에 꼭 필요하면 관리자 승인을 받은 제한시간 접근을 발급하고 접근 이력을 남긴다.

## 10. 관리자 수정·롤백

### 10.1 제공 행동

- `입금 확인 취소`
- `이전 단계로 되돌리기`
- `다른 단계로 이동`
- `담당자 변경`
- `준등기번호 수정`
- `우체국 전달 취소`
- `발송 처리 취소`
- `완료 주문 다시 열기`
- `휴지통으로 이동`
- `휴지통에서 복구`

모든 행동은 관리자만 실행한다.

### 10.2 롤백 사전 점검 API

프론트는 바로 상태를 바꾸지 않는다. 먼저 서버에 목표 단계를 보내 영향 분석 결과를 받는다.

```json
{
  "orderNumber": "PE-2026-000139",
  "target": {
    "paymentStatus": "PENDING",
    "productionStage": "BLOCKED"
  }
}
```

응답:

```json
{
  "allowed": true,
  "warnings": [
    {
      "type": "NOTIFICATION_ALREADY_SENT",
      "templateCode": "PAWEVER_PRODUCTION_STARTED",
      "templateName": "제작 시작 안내",
      "sentAt": "2026-09-10T11:32:00+09:00",
      "recipientMasked": "010-29**-03**"
    }
  ],
  "downstreamTasks": 3,
  "downstreamArtifacts": 2,
  "requiresCustomerFollowUp": true,
  "requiresAcknowledgement": true
}
```

### 10.3 알림톡 발송 이력이 있는 롤백 모달

제목:

> 이 주문을 입금 확인 필요 단계로 되돌릴까요?

본문 필수 내용:

> 이 주문에는 다음 알림톡이 이미 발송되었습니다.

- 제작 시작 안내 · 2026. 09. 10. 11:32 · 발송 성공
- 수신 번호 · 010-29**-03**

경고 문구:

> 이미 발송된 알림톡은 회수되지 않습니다. 이전 단계로 되돌려도 같은 알림톡은 자동으로 다시 발송되지 않으며, 고객에게 별도 안내가 필요할 수 있습니다.

필수 입력:

- 롤백 사유 코드
- 상세 메모
- `발송 이력과 고객 안내 필요 여부를 확인했습니다` 확인 항목

행동 이름:

- 주 행동: `입금 확인 필요로 되돌리기`
- 보조 행동: `취소`

서버 처리:

1. 현재 버전이 사전 점검 시점과 같은지 확인한다.
2. 롤백 이벤트를 새로 기록한다.
3. 이후 단계의 미완료 작업은 `SUPERSEDED`로 닫는다. 삭제하지 않는다.
4. 이미 생성된 파일은 보존 기간까지 유지하고 새 작업에서 재사용 여부를 선택할 수 있게 한다.
5. 기존 알림 발송 이력은 그대로 유지한다.
6. 같은 알림톡의 자동 재발송을 금지한다.
7. `CUSTOMER_CONTACT_REQUIRED` 이슈를 생성한다.
8. 관리자는 `별도 안내 완료` 또는 `안내 불필요`와 사유를 기록해 이슈를 닫는다.

알림톡 발송 이력이 없고 하위 작업도 없는 단순 직전 단계 롤백은 사유 입력과 확인만 요구한다.

### 10.4 알림 재발송

상태를 다시 앞으로 이동해도 과거 이벤트에 연결된 알림은 자동 재발송하지 않는다. 관리자가 알림 내용을 미리 확인하고 재발송 사유를 입력한 경우만 새 발송 시도를 만든다.

## 11. 삭제·휴지통·복구

복구 허용 역할은 이 원문과 최종 이관서가 충돌한다. 개발 보완서 Q3 답변 전에는 새로운 복구 역할을 운영에 부여하지 않는다. 보존 대상 거래 기록은 아래 §11.3의 분리 보관 규칙을 유지한다.

### 11.1 휴지통 이동

- 관리자만 가능하다.
- 삭제 사유를 필수로 받는다.
- `deletedAt`, `deletedBy`, `deleteReason`, `purgeAt=deletedAt+30일`을 저장한다.
- 삭제 직전의 모든 상태와 담당자를 복구 스냅샷으로 저장한다.
- 일반 업무 뷰, 통계의 활성 건수, 자동 배정, 예약 알림에서 즉시 제외한다.
- S3 파일과 DB 행은 30일 동안 유지한다.
- 진행 중 작업은 `SUSPENDED_BY_TRASH`로 일시 중지한다.

### 11.2 복구

- 관리자만 가능하다.
- 30일 안에 `주문 복구`를 실행할 수 있다.
- 삭제 직전 상태·담당자·작업을 복원한다.
- 예약 알림은 자동 재활성화하지 않는다. 관리자가 현재 상태를 확인한 뒤 다시 예약한다.
- 복구 시 이미 기한이 지난 주문은 자동 취소하지 않고 `복구 후 확인 필요` 이슈를 만든다.
- 복구와 동시에 과거 알림을 다시 발송하지 않는다.

### 11.3 영구 파기

- 기본은 `purgeAt` 도달 후 자동 실행이다.
- 개인정보 파기 요청은 관리자가 30일 전 즉시 영구 파기를 실행할 수 있다.
- 즉시 영구 파기는 주문번호 재입력과 최종 확인을 요구한다.
- 원본 사진, 파생 이미지, 모델링 파일, 주소, 전화번호 등 고객 연결 데이터를 삭제한다.
- 법정 보존이 필요한 거래 기록은 개인정보 최소화 또는 분리 보관 정책을 따른다.
- 파기 성공 여부와 삭제된 S3 객체 수를 감사 로그에 남긴다.
- 파기 후에는 복구할 수 없다.

### 11.4 담당자 계정 삭제 요청

작업자 계정은 감사 로그의 행위자이므로 물리 삭제하지 않고 관리자만 비활성화한다.

1. 비활성화 전 활성 작업 수와 기본 담당 역할을 사전 점검한다.
2. 활성 작업이 있으면 새 담당자를 지정해야 비활성화할 수 있다.
3. 신규 작업 기본 담당자로 지정된 계정이면 대체 계정을 먼저 지정한다.
4. 비활성화된 계정은 로그인·작업 수락·파일 열람을 할 수 없다.
5. 과거 작업과 감사 로그에는 당시 담당자 이름과 계정 식별자를 유지한다.
6. 관리자는 비활성 계정을 다시 활성화할 수 있다.
7. 마지막 활성 OWNER 계정은 비활성화할 수 없다.

## 12. SLA 설정

### 12.1 설정값

```json
{
  "enabled": false,
  "businessDays": 7,
  "timezone": "Asia/Seoul",
  "effectiveAt": null,
  "updatedBy": "admin-account-id"
}
```

초기값은 `enabled=false`, `businessDays=7`이다.

### 12.2 ON/OFF 규칙

- 관리자만 변경할 수 있다.
- 토글 이름은 ON 상태를 설명하는 `제작·발송 기한을 적용`으로 사용한다.
- ON으로 바꿀 때 적용 시작 시각과 7영업일 기준을 확인한다.
- ON 이후 입금 확인된 주문부터 `slaEnforced=true`와 `dueAt`을 스냅샷으로 저장한다.
- 기존 주문에 소급 적용하지 않는다.
- OFF로 바꿔도 과거 주문의 계산값은 삭제하지 않지만 신규 초과 판정과 자동 경고를 중지한다.
- 영업일은 월~금에서 관리자가 등록한 대한민국 공휴일을 제외한다.
- 마감 시각은 입금 확인 시각과 동일한 시각으로 계산한다.

### 12.3 지연 알림

SLA 초과만으로 지연 알림톡을 자동 발송하지 않는다. 지연 사유와 변경 예정일에 사람 판단이 필요하기 때문이다.

1. 시스템이 `SLA_OVERDUE` 이슈를 만든다.
2. 관리자가 기존 예정일, 변경 예정일, 지연 사유를 확인한다.
3. `지연 안내 발송`을 실행한다.
4. 발송 성공 후 이슈에 안내 완료 시각을 기록한다.

## 13. 알림톡 정책

### 13.1 발송 원칙

- 주문 상태와 알림 발송은 한 트랜잭션으로 직접 묶지 않고 도메인 이벤트와 발송 큐로 연결한다.
- `NotificationDispatch.idempotencyKey`에 유일 제약을 둔다.
- 상태 변경이 재시도돼도 같은 이벤트의 알림은 한 번만 발송한다.
- 발송 실패가 주문 상태를 원복시키지는 않는다. `NOTIFICATION_FAILED` 이슈를 만든다.
- 고객 전화번호 전체와 사진 URL을 Telegram에 보내지 않는다.
- 알림 내용과 변수는 발송 시점의 값으로 보존한다.

### 13.2 발송 매트릭스

| 이벤트 | 템플릿 | 자동 여부 | 조건 |
|---|---|---:|---|
| 랜딩 계좌이체 주문 접수 | `0903_굿즈_입금요청_알림톡` | 자동 | bank transfer 주문당 1회 |
| 외부 채널 선결제 주문 접수 | `0820_굿즈_신청완료_알림톡` | 자동 | 스마트스토어·와디즈 등 선결제만 |
| 모델 내부 검수 통과 | 신규 제작 시작 안내 | 자동 | 신규 템플릿 승인 후 주문당 1회 |
| 배송비 별도 입금 확인 | `0831_배송비_입금확인_알림톡` | 조건부 | 무료·체험단 배송비 주문만 |
| 제작·배송 지연 | `0831_제작배송지연_알림톡` | 관리자 확인 | 기존·변경 예정일과 사유 필수 |

## 14. 준등기 엑셀

### 14.1 우체국 전달용 내보내기

포함 조건:

- `deliveryMethod=SHIPPING`
- `productionStage=PACKING`
- `shipmentStatus=NOT_READY`
- 휴지통이 아님
- 필수 주소·연락처가 모두 있음
- 다른 미완료 ShipmentExportBatch에 포함되지 않음

XLSX는 첫 행부터 데이터가 시작되며 열 이름 행을 만들지 않는다. 열 순서와 형식은 아래 값으로 고정한다.

| 열 위치 | 값 | XLSX 셀 형식 | 변환 규칙 |
|---:|---|---|---|
| A | 보호자명 | 텍스트 | 수령자 이름 원문 |
| B | 우편번호 | 텍스트 | 앞자리 0 보존, 숫자형 셀 금지 |
| C | 주소 | 텍스트 | 기본 주소 |
| D | 이하 주소 | 텍스트 | 상세 주소 |
| E | 전화번호 | 텍스트 | 숫자 이외 문자를 제거해 `01000000000` 형태로 출력 |
| F | 반려동물 이름 | 텍스트 | 반려동물 이름 원문 |

금지 사항:

- 헤더 행 추가 금지
- 주문번호 열 추가 금지
- 셀 병합 금지
- 우편번호와 전화번호를 숫자 셀로 저장하는 것 금지
- 전화번호에 하이픈, 공백, 괄호 포함 금지
- 빈 주소를 임의 문자열로 채우는 것 금지

전화번호는 정규화 후 `010`으로 시작하는 11자리인지 검증한다. 우편번호는 문자열 5자리인지 검증한다. 실패한 주문과 수정할 필드를 정확히 반환한다.

워크북은 `.xlsx`, 첫 번째 시트만 사용한다. 시트 이름은 `준등기`로 한다.

내보내기 파일에는 주문번호가 없으므로 서버는 별도로 다음 스냅샷을 저장한다.

```text
exportBatchId, rowNumber, orderId,
guardianName, postalCode, address, addressDetail, normalizedPhone, petName,
rowFingerprint, exportedAt, exportedBy
```

`rowFingerprint`는 여섯 필드를 정규화해 만든 내부 비교용 해시다. 엑셀에는 넣지 않는다.

내보낸 파일명 예: `pawever_postoffice_20260910_batch-004.xlsx`

트랜잭션 규칙:

1. 선택한 모든 주문을 잠그고 검증한다.
2. 엑셀 바이트와 ShipmentExportBatch를 생성한다.
3. 배치 생성이 성공하면 주문을 `AWAITING_POST_OFFICE_RESULT`로 이동한다.
4. 응답 다운로드가 실패해도 같은 배치 파일을 다시 내려받을 수 있어야 한다.
5. 같은 요청이 재시도돼도 새 배치를 중복 생성하지 않는다.

### 14.2 결과 가져오기

우체국이 돌려주는 파일에는 내보낸 여섯 필드와 준등기번호가 포함된다고 가정한다. 정확한 열 위치는 실제 샘플 파일을 받은 뒤 parser 설정으로 확정한다.

비교는 단순 행 번호가 아니라 내보내기 스냅샷과 반환 행의 정규화된 여섯 필드를 기준으로 한다. 반환 순서가 바뀌어도 매칭되어야 한다.

비교 결과 분류:

| 결과 | 조건 | 기본 처리 |
|---|---|---|
| `MATCHED` | 여섯 필드가 정확히 일치하고 준등기번호 정상 | ACCEPTED 처리 가능 |
| `MISSING` | 내보냈지만 반환 파일에 없음 | 결과 대기 유지 |
| `EXTRA` | 반환 파일에만 존재 | 자동 주문 생성 금지, 관리자 확인 |
| `CHANGED` | 전화번호·반려동물 등 일부만 일치 | 추천 주문을 보여주되 자동 연결 금지 |
| `AMBIGUOUS` | 같은 여섯 필드 후보가 여러 개 | 관리자 수동 연결 |
| `DUPLICATE_TRACKING` | 준등기번호가 다른 주문에 사용됨 | 반영 차단 |
| `INVALID_TRACKING` | 준등기번호가 숫자 13자리가 아님 | 수정 후 재처리 |
| `ALREADY_APPLIED` | 같은 주문·같은 준등기번호가 이미 반영됨 | 중복 성공, 알림 재발송 없음 |

비교 결과 모달 필수 내용:

- 전체 반환 행 수
- 정상 매칭 수
- 누락 수
- 추가 수
- 정보 변경·중복·준등기번호 오류 수
- 각 오류 행의 반환 값, 추천 주문, 기존 내보내기 값

관리자 행동:

- `추천 주문에 연결`
- `다른 주문 검색`
- `배송 정보 수정`
- `준등기번호 수정`
- `이 행 제외`
- `주문을 휴지통으로 이동`
- `수정한 행 다시 처리`

`이 행 제외`는 반환 파일의 추가 데이터를 무시하는 것이고 주문 삭제가 아니다. `주문을 휴지통으로 이동`만 주문 소프트 삭제를 실행한다.

정상 행은 관리자가 비교 결과를 확인한 뒤 일괄 확정한다. 오류 한 행 때문에 정상 행을 막지 않는다.

정상 반영된 행은 되돌리지 않는다.

## 15. 핵심 데이터 모델

### 18.2 저장 규칙

- S3 버킷은 비공개다.
- DB에는 URL이 아니라 객체 키를 저장한다.
- 다운로드 URL은 서버가 권한을 확인한 뒤 짧게 발급한다.
- 미리보기와 다운로드를 별도 감사 이벤트로 기록한다.
- Telegram·알림톡 JSON·애플리케이션 로그에 원본 URL을 남기지 않는다.
- 고객 원본과 고객에 연결된 파생 파일은 배달 완료 후 90일 보관 후 파기한다.
- 미입금 만료 주문은 만료 처리와 함께 사진 파기 대상으로 등록한다.
- 재제작·분쟁 주문은 사건 종료 후 90일까지 보관한다.
- 포트폴리오 활용은 별도 명시 동의와 별도 자산 복사 정책 없이는 허용하지 않는다.

## 20. 오류 처리

| 상황 | 처리 |
|---|---|
| 같은 주문을 두 명이 동시에 변경 | 한 요청만 성공, 다른 요청은 409와 최신 상태 반환 |
| 상태 완료에 필수 파일 누락 | 전이 차단, 누락 파일명을 정확히 반환 |
| 알림톡 제공자 실패 | 주문 상태 유지, 발송 실패 기록, 이슈 생성, 동일 키 재시도 |
| 준등기 엑셀 일부 오류 | 정상 행 커밋, 오류 행만 수정 목록으로 유지 |
| 우체국 반환 행이 내보낸 데이터보다 적음 | 누락 주문을 결과 대기로 유지하고 MISSING으로 표시 |
| 우체국 반환 파일에 추가 행이 있음 | 주문을 자동 생성하지 않고 EXTRA로 표시 |
| 반환 데이터 일부만 바뀜 | 추천 매칭만 제시하고 관리자 확인 전 연결 금지 |
| 이미 반영된 같은 준등기번호 재업로드 | 중복 성공, 상태·알림 변화 없음 |
| 다른 주문에 같은 준등기번호 | 충돌 행 차단 |
| 휴지통 주문에 자동 작업 실행 | 작업 건너뛰고 감사 로그 기록 |
| 롤백 대상이 사전 점검 후 변경됨 | 전이 차단, 영향 분석 다시 요구 |
| 파기할 S3 객체 일부 실패 | 성공한 객체 기록, 실패 객체 재시도, 주문 파기 완료 처리 금지 |
| 권한 변경 중 대상 계정이 작업을 처리함 | 계정 권한 버전 검사, 변경 후 다음 요청부터 새 권한 강제 |
| 마지막 OWNER 권한 해제·비활성화 시도 | 요청 차단, 다른 OWNER를 먼저 지정하도록 안내 |
| 초대 토큰 만료·재사용 | 활성화 차단, 관리자에게 재초대 요청 안내 |

대량 작업 응답은 `성공`, `건너뜀`, `실패`와 주문별 사유를 분리한다.

## 21. 인수 조건

### 21.1 입금

- 관리자가 PAYMENT_CHECK 주문을 상세 진입 없이 입금 확인할 수 있다.
- 확인자·시각이 기록된다.
- 같은 요청 재시도는 한 번만 처리된다.
- 입금 확인 취소는 관리자만 가능하고 사유가 남는다.

### 21.2 제작

- 입금 확인 후 박신형의 모델링 작업이 자동 생성된다.
- 박신형에게 보호자 연락처와 주소가 응답되지 않는다.
- 필수 파일이 없으면 모델링 완료가 차단된다.
- 모델 승인 후 박나혜의 색상 작업이 자동 생성된다.
- 제작 보조 계정 활성화 후 신규 PRINT_FINISHING 작업 기본 담당자를 변경할 수 있다.
- 기존 진행 주문은 관리자 명시 행동 없이는 자동 재배정되지 않는다.

### 21.3 플레이트·검수·정산

- 한 플레이트 시작·완료로 연결 주문이 함께 이동한다.
- 실패한 주문만 정상 주문과 분리된다.
- 주문당 작업자 한 명만 3,000원 정산 대상이 된다.
- 재시도 때문에 정산이 중복 생성되지 않는다.

### 21.4 준등기

- 선택한 배송 주문의 검증이 모두 통과해야 포장 완료와 엑셀 생성이 함께 실행된다.
- XLSX 첫 행부터 데이터가 시작되고 헤더가 없다.
- 열은 보호자명, 우편번호, 주소, 이하 주소, 전화번호, 반려동물 이름 순서의 정확히 6개다.
- 우편번호와 전화번호는 텍스트 셀이며 전화번호에는 하이픈이 없다.
- 파일 생성 후 주문은 AWAITING_POST_OFFICE_RESULT로 이동한다.
- 결과 파일의 정상 행만 발송 완료와 알림 발송으로 이어진다.
- 누락·추가·변경·중복·준등기번호 오류가 서로 다른 비교 결과로 노출된다.
- 오류 행은 연결·수정·제외·휴지통 이동 후 개별 재처리할 수 있다.
- 현장 수령 주문은 준등기번호를 요구하지 않는다.

### 21.5 직접 수령

- 직접 수령 신청은 상상관 또는 다빈치관 중 하나를 반드시 가진다.
- 포장 완료 후 READY_FOR_PICKUP으로 이동한다.
- 상상관과 다빈치관 대기 목록을 분리 조회할 수 있다.
- PICKED_UP 전에는 관리자가 장소를 변경할 수 있다.
- 수령 완료 후 주문은 COMPLETED가 된다.

### 21.6 롤백·알림

- 롤백 전 영향 분석이 실행된다.
- 넘어가는 구간에 발송 성공 알림톡이 있으면 템플릿명·발송 시각·마스킹 번호가 모달에 표시된다.
- 관리자가 확인하지 않으면 롤백할 수 없다.
- 롤백 후 과거 알림이 자동 재발송되지 않는다.
- 고객 안내 필요 이슈가 생성된다.

### 21.7 휴지통

- 관리자만 주문을 휴지통으로 이동할 수 있다.
- 삭제 주문은 모든 활성 업무 뷰와 자동화에서 제외된다.
- 30일 안에 관리자가 삭제 직전 상태로 복구할 수 있다.
- 복구 시 알림이 자동 재발송되지 않는다.
- 영구 파기 후에는 복구할 수 없다.

### 21.8 SLA

- 초기 설정은 OFF다.
- OFF 상태에서는 신규 기한 초과 이슈와 지연 자동 행동이 발생하지 않는다.
- ON 이후 입금 확인 주문에만 7영업일 기한이 적용된다.
- 설정 변경자와 변경 시각이 남는다.

### 21.9 계정·권한

- 관리자가 이메일로 계정을 초대할 수 있다.
- 이메일 주인만 24시간 유효 일회용 링크로 비밀번호를 설정할 수 있다.
- 이메일은 정규화된 고유 로그인 아이디다.
- OWNER가 사람별 데이터 노출과 행동 권한을 ON/OFF할 수 있다.
- 역할 기본 권한보다 계정별 DENY가 우선한다.
- 권한 변경은 다음 요청부터 즉시 적용되고 변경 이력이 남는다.
- 배정 범위 밖 주문은 보기 권한이 ON이어도 접근할 수 없다.
- 마지막 OWNER의 필수 권한 해제와 계정 비활성화는 차단된다.

### 21.10 접근성·업무 연속성

- 핵심 업무는 키보드만으로 완료 가능하다.
- 모든 행동에 명확한 동사형 이름이 있다.
- 모달의 초점이 내부에 머물고 닫으면 원래 위치로 돌아간다.
- 처리 결과와 오류가 보조기술에 전달된다.
- 필터와 현재 목록 위치는 상세 확인·작업 완료 후에도 유지된다.

## 22. 구현 순서

### 1단계: 상태와 감사 기반

- 분리 상태 모델과 데이터 마이그레이션
- 작업·이슈·감사 이벤트 테이블
- optimistic lock와 idempotency
- OWNER·역할 기본 권한·사람별 permission override
- 이메일 초대·최초 비밀번호 설정·세션 즉시 무효화
- 서버 데이터 노출 경계

### 2단계: 관리자 정상 흐름

- 입금 직접 확인
- 업무 뷰 계산
- 담당자 배정
- 제작 단계 전이와 필수 파일 검증
- 현재 박나혜 기본 배정

### 3단계: 알림과 안전한 수정

- 알림톡 발송 큐와 템플릿 변수 매핑
- 제작 시작 신규 템플릿 연결
- 롤백 사전 점검과 알림 발송 이력 경고
- 휴지통·복구·30일 파기

### 4단계: 플레이트와 준등기

- PrintBatch와 주문 연결
- 배치 단위 출력 처리
- 배송 주문 다중 선택 포장 완료
- 헤더 없는 6열 XLSX 생성·재다운로드
- 결과 엑셀 비교·부분 성공·누락·추가·변경·오류 수정
- 상상관·다빈치관 직접 수령 흐름

### 5단계: 관리자 판단 지표

- 단계별 적체와 최장 대기
- 담당자별 활성 작업
- 출력 실패·재제작·추가 원가
- SLA 토글과 ON 상태 지표

### 6단계: 외부 채널과 후속 자동화

- 스마트스토어·와디즈 주문 정규화
- 우체국 배달 상태 연동 검증
- 은행·주문 파일 가져오기
- Notion 요약 동기화

각 단계는 이전 단계가 운영 환경에서 동작하고 감사 로그·복구가 검증된 뒤 진행한다.
