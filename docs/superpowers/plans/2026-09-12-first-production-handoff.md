# 1차 개발 계획 — 입금 확인부터 모델링·검수 인계까지

작성일: 2026-09-12. 상태: 1차 구현·로컬 자동 검증 완료, 운영 적용 대기. [실제 구현·검증·잔여 적용 항목](../../operations/2026-09-12-first-flow-implementation.md)을 함께 읽는다.
목표: 관리자 웹에서 입금 확인 → 모델링 담당자의 내 작업 → 자료 등록·모델링 완료 → 검수 담당자의 내 작업으로 한 주문이 이어진다.

## 1. 이번에 완성할 사용자 흐름

**종무님:** 입금 대기 주문을 열어 예상 금액·입금자 정보를 확인하고 실제 입금을 대조한다. 입금 확인을 누르면 확인자·시각을 남기고 모델링 작업을 한 번 생성한다. 주문 목록에서 결제 상태, 제작 단계, 담당자를 각각 확인한다.

**모델링 담당자:** 로그인하면 자신에게 배정된 작업을 본다. 주문의 고객 사진, 반려동물 이름, 상품 옵션·키링 여부를 확인하고 작업 시작을 누른다. 4면도, 모델 원본, STL/3MF를 등록한 뒤 모델링 완료를 누른다. 그러면 모델링 작업은 완료되고 검수 작업이 한 번 생성된다.

**검수 담당자:** 자신의 내 작업에 같은 주문이 나타난다. 고객 사진과 모델링 결과물을 열어볼 수 있다. 첫 완료 기준은 여기까지다. 내부 검수의 승인·수정 요청 및 이후 색상·출력·포장 흐름은 후속 개발에 연결한다. 모델링 완료만으로 제작 시작 알림을 보내지 않는다. 원래 요구의 발송 시점은 내부 검수 통과 후다.

**화면 범위.** 기존 AdminOrders에 결제/제작/담당자와 주요 행동을 추가한다. AdminMyWork를 만들어 배정된 작업의 시작·상세·완료를 제공한다. 기존 AdminOrderPanel을 확장해 사진, 모델 파일 등록, 필요한 자료와 이력을 보여준다. 기본 담당자 설정은 기존 계정 관리 영역에서 모델링/검수 두 역할의 계정을 지정하는 최소 UI로 제공한다. 계정마다 별도 주문 화면을 새로 만들지 않는다.

**판정에 사용할 대표 주문.** 테스트용 새 유료 주문 한 건으로 위 흐름을 세 계정에서 확인한다. 무료 주문은 결제를 받은 것으로 표시하지 않고 별도의 적격성 테스트로 검증한다. 과거 제작 중 주문은 일괄 모델링 대기로 돌리지 않는다.

이번 범위는 전체 이관 계획 중 상태·담당자·입금·작업 인계의 첫 부분이다. Notion 실연동, 이후 제작 단계의 실행 UI, 우체국 엑셀, 새 고객 알림 발송, 휴지통, SLA, 정산은 별도 후속 작업이다. 다만 기존 접수·취소·배송·수령 처리를 깨뜨리지 않는 연결과 회귀 검증은 이번 전환 작업에 포함한다.

기준 자료는 [개발 보완서](../../operations/2026-09-12-development-addendum.md), [운영 명세](../specs/2026-09-10-pawever-admin-operations-ux-design.md), [전체 구현 계획](2026-09-11-pawever-admin-notion-integration.md)다. 시작 시점 로컬 HEAD는 백엔드 c9af267, 랜딩 e99eade, migration V16이다. 입금 기한 기본값은 두 채널 모두 7일이며 기존 주문에 저장된 만료 시각은 별도 근거 없이 다시 계산하지 않는다.

## 2. 작업 단위와 완료 조건

각 작업은 실패 테스트 또는 재현 확인 → 최소 구현 → 관련 검사 → 변경 검토 순서로 수행한다. 아래 파일 중 ‘신규’는 만들 위치 제안이며 현재 존재한다고 가정하지 않는다. 작업 번호는 의존 관계를 설명하기 위한 것이며 migration 번호나 배포 횟수가 아니다.

**W01. 현재 주문 기능의 기준선과 첫 흐름 계약 고정**

산출물: 기존 검사 결과 기록, 역할별 목록/상세 응답 예시, 첫 흐름의 전이·오류 사례. 대상은 기존 GoodsSurveyServiceTest, GoodsOrderServiceTest, GoodsSurveyRetentionServiceTest, AdminOrderServiceTest와 프론트 adminApi/adminOrderStatus 관련 테스트다. 부족한 사례만 추가한다.

전이는 결제 PENDING/제작 BLOCKED → 결제 CONFIRMED/모델링 대기 → MODELING → MODEL_REVIEW다. 목록은 orderNumber, petName, goodsType/키링, paymentStatus, productionStage, assignee, blockingIssues, allowedActions, version을 포함한다. 제작자에게 고객 연락처·주소·결제 상세를 내려주지 않는다. 내부 결제 상태로 작업 가능 여부를 판단하되 제작 화면은 불필요한 결제 정보를 표시하지 않는다.

완료 조건: 7일 기한, 가격/키링/배송비 스냅샷, 정원 반환, 온라인 재신청과 FLEA 복수 주문, 주소 없는 수령, 기존 취소·배송 경로의 기준선 결과를 기록한다. 현재 전체 테스트를 실행하고 실패가 있으면 원인과 재현을 기록한다. 이전 대화의 통과 개수를 현재 결과로 사용하지 않는다. 의존: 없음.

**W02. 분리 상태·작업·감사·중복 방지 저장 기반**

산출물: 새 Flyway migration, 상태 enum, 작업/파일/이슈/감사/명령 기록 모델 및 repository. 기존 GoodsSurveyFulfillment와 관리자 DTO를 수정하고 production/, issue/, 공통 명령 처리 위치를 추가한다. 기존 S3 클라이언트·관리자 계정을 재사용한다.

저장 책임은 주문의 분리 상태와 version, 결제 확인 내역, production_tasks, production_artifacts, issues, audit_events, 변경 명령 멱등 기록으로 나눈다. task는 주문+단계+attempt의 유일성을 지키고 담당자, 시작/완료 시각을 저장한다. 한 주문에 두 상태 모델이 서로 독립적으로 쓰이게 만들지 않는다. 개발 중 구필드를 보존하더라도 원본 전환·제거 시점은 W09에서 명시한다. 외부 이벤트가 필요하면 같은 트랜잭션의 outbox 기반만 준비하고 새 발송 worker는 이 범위에서 켜지 않는다.

완료 조건: 같은 명령이 동시에 와도 결과/작업이 한 번 생기고, 같은 키에 다른 본문은 충돌 처리한다. 감사와 상태 중 하나만 저장되는 부분 실패가 없다. 격리된 MariaDB에서 V16 데이터에 migration을 적용해 검증한다. 적용된 migration은 다시 수정하지 않는다. 필요한 이슈/명령 테이블보다 backfill을 먼저 실행하지 않는다. 의존: W01.

**W03. 직원 역할·실제 권한·기본 담당자 연결**

산출물: 역할/업무 역할/권한 계산, 현재 로그인 계정 조회, 담당자 배정과 기본값 설정 API. 기존 AdminRole, AdminAccountService, AdminAuthenticationFilter, SecurityConfig, AdminTokenProvider 및 관련 컨트롤러를 수정한다. 신규 EffectivePermissionService와 로그인 계정 응답 DTO를 추가한다. 현재 사용자 조회는 보호되는 GET /api/admin/me로 두고 공개 /api/admin/auth/** 아래에 추가하지 않는다.

서버에서 원본 명세와 보완서의 권한을 계산한다. OWNER/ADMIN과 모델링/검수 담당자의 작업 범위를 구분한다. MARKETING/SUPPORT는 이번 제작 업무와 개인정보를 자동 허용하지 않는다. 모델링·검수 기본 담당자는 기존 활성 계정 중 해당 workRole을 가진 계정으로 지정하며 사람 이름이나 임의 account ID를 코드에 고정하지 않는다. 기본값 변경은 새 작업부터, 기존 작업 재배정은 명시적 행동으로 적용한다.

완료 조건: /api/admin/**와 /api/production/**에서 직원 토큰만 인정하며 역할/계정 변경이 다음 요청부터 반영된다. CORS는 필요한 PATCH·Idempotency-Key를 허용한다. 다른 담당자 주문의 사진·파일에 직접 접근해도 거절된다. 자기 권한 변경과 마지막 OWNER 상실을 막는다. 첫 OWNER는 기존 관리자를 일괄 승격하지 않고 운영자가 확인한 계정에 명시적으로 부여한다. 의존: W01; 저장 구현은 W02.

**W04. 입금 확인과 모델링 작업 생성**

산출물: ManualPaymentService 및 POST /api/admin/orders/{orderNumber}/payments/confirm. 기존 AdminOrderService.changeStatus와 GoodsOrderService의 수기 결제 처리·가격 스냅샷을 재사용한다. 기존 일반 상태 변경으로 새 입금 확인 로직을 우회하지 못하게 한다.

입금 확인은 CONFIRM_PAYMENT와 관련 데이터 권한, version, 멱등 키를 검사하고 실제 확인 금액·확인자·시각을 저장한다. 금액이 다르면 정상 확인으로 넘기지 않고 PAYMENT_MISMATCH로 남긴다. 정상 확인 후 기본 모델링 담당자에게 작업을 생성한다. 담당자가 없거나 비활성이면 실제 입금 사실은 유지하고 UNASSIGNED와 미배정 작업을 남겨 관리자가 배정할 수 있게 한다. 사진 부족도 입금 취소로 되돌리지 않고 차단 사유로 표시한다.

완료 조건: 반복 클릭과 동시 요청에도 입금 시각을 덮거나 모델링 작업을 중복 생성하지 않는다. 미입금 주문은 작업 시작을 할 수 없다. 무료 주문은 NOT_REQUIRED를 유지하며 명시적 배정 또는 검증된 이전 절차에서 작업을 한 번 생성한다. 의존: W02, W03.

**W05. 내 작업 조회·착수와 서버 행동 계산**

산출물: ProductionWorkflowService, AllowedActionService, ProductionTaskController. GET /api/production/my-tasks, POST /api/production/tasks/{taskId}/start, 주문별 권한 필터링 상세 응답을 제공한다. 기존 사진 링크·접근 로그 기능에 작업 배정 범위 검사를 연결한다.

모델링 작업을 시작하면 task를 IN_PROGRESS로, 주문 제작 단계를 MODELING으로 함께 바꾼다. 내 작업은 현재 배정된 미완료 작업을 기본으로 조회한다. 가능한 행동은 서버 allowedActions가 정하며, 시작 시에도 권한·결제 적격성·차단 사유를 재검사한다. 관리자 강제 상태 이동으로 정상 작업의 완료 조건을 우회하지 않는다.

완료 조건: 담당자는 자기 작업만 착수할 수 있다. 미배정/자료 부족/미입금/종결 주문은 정확한 사유로 막힌다. 늦은 version으로 수정하면 409와 권한에 맞는 최신 요약을 받는다. 의존: W02, W03; 입금부터 이어지는 통합 검증은 W04.

**W06. 모델링 자료 업로드·확인·열람**

산출물: production_artifacts 처리 서비스와 업로드 요청/확인/다운로드 API. 경로는 POST /api/production/tasks/{taskId}/artifacts/upload-requests, POST /api/production/artifacts/{artifactId}/confirm, POST /api/production/artifacts/{artifactId}/download-link로 제안한다. 기존 GoodsSurveyPhotoStorage와 S3 클라이언트의 서명 URL·객체 확인 동작을 활용하되 고객 사진의 허용 형식을 모델 파일에 그대로 적용하지 않는다.

서버가 해당 작업에 속한 object key를 발급하고 파일 종류·크기·등록자·버전을 저장한다. 완료 확인은 실제 S3 객체와 등록 정보를 대조한다. 종류별 허용 형식/크기와 모델 원본 형식은 구현 전에 업로드 계약으로 명시하고 운영팀의 실제 샘플로 확인한다. 사진·모델 파일에 공개 URL을 영구 저장하지 않는다. 실패한 업로드를 완료 파일로 세지 않는다.

완료 조건: 4면도, 모델 원본, STL/3MF를 구분해 등록·조회한다. 다른 작업의 object key 재사용, 권한 없는 다운로드, 미완료 업로드는 거절된다. 검수 담당자에게 인계된 뒤에는 해당 주문의 결과물을 볼 수 있다. 자동 3D 생성이나 웹 3D 뷰어는 필수 산출물이 아니다. 의존: W02, W03; 실제 작업 연결은 W05.

**W07. 모델링 완료 → 검수 작업 생성**

산출물: POST /api/production/tasks/{taskId}/complete와 원자적 다음 작업 생성. ProductionWorkflowService에 정상 인계 전이를 구현한다.

본인 배정과 COMPLETE_MODELING, 시작된 작업, 현재 version, 필수 확정 파일과 차단 이슈를 검사한다. 성공 시 모델링 task 완료, 주문 MODEL_REVIEW, 검수 task 생성, 검수 담당자 배정과 감사 이벤트를 같은 트랜잭션에 기록한다. 현재 검수 기본 담당자가 없으면 모델링 결과는 보존하고 검수 task를 미배정+이슈로 남긴다. 관리자가 배정하면 검수자의 내 작업에 표시한다.

완료 조건: 두 번 완료해도 검수 task는 한 건이다. 필수 파일이 없으면 빠진 파일을 안내하고 상태를 유지한다. 동시에 재배정/취소/완료가 발생하면 한 가지 일관된 결과만 남긴다. 검수자는 원본 사진과 모델링 파일을 읽을 수 있고, 무관한 직원은 접근하지 못한다. 의존: W04, W05, W06.

**W08. 관리자·제작자 화면 연결**

산출물: 기존 client/src/lib/adminApi.ts, AdminShell.tsx, AdminOrders.tsx, AdminOrderPanel.tsx, AdminAccounts.tsx, App.tsx 수정. 신규 AdminMyWork.tsx, adminContracts.ts와 첫 흐름에 필요한 테스트. 새 경로는 /admin/my-work로 제안한다.

입금 확인 화면은 확인 결과와 모델링 배정을 표시한다. 제작자는 내 작업에서 시작과 완료를 누르고 상세에서 파일을 등록한다. 검수자는 자신에게 넘어온 작업과 자료를 본다. 메뉴·역할·권한은 /api/admin/me 응답으로 판단하며 저장된 JWT role만 믿지 않는다. 새 흐름의 버튼은 allowedActions만 사용한다. 첫 화면의 작업 상태와 이력은 새로고침 후에도 서버 결과와 같아야 한다.

완료 조건: 필수 자료 부족, 미배정, 저장 실패, 409 충돌이 화면에서 해결 가능한 메시지로 나타난다. 상세를 닫아도 검색·필터·페이지가 유지된다. 모바일에서 작업 시작/완료가 가능하다. 신규 흐름으로 옮긴 전이 규칙만 adminOrderStatus.ts에서 제거하고, 배송·수령 등 남은 사용처를 확인하기 전 파일 전체를 삭제하지 않는다. 의존: API 형태 확정은 W01/W03; 실제 연결 완료는 W04~W07.

**W09. 전체 흐름 검증과 실제 주문 전환 준비**

산출물: e2e/admin-modeling-handoff.spec.ts, MariaDB migration 검증 결과, 전환 대상·보류 주문 보고와 배포/복구 절차. 샘플 파일은 비식별 테스트 자료를 사용한다.

세 테스트 계정으로 입금 확인 → 모델링 목록 확인 → 착수 → 파일 등록 → 완료 → 검수 목록/파일 열람을 실행한다. 중복 클릭, 자료 부족, 다른 계정 접근, 담당자 변경, 미배정, 동시 수정, 무료 주문을 함께 검증한다. 백엔드 전체 test와 랜딩 pnpm test/check/build를 실행하고 첫 흐름 및 기존 접수·배송·수령의 관련 E2E를 통과시킨다. 운영 자료가 필요한 검증은 테스트 데이터 성공으로 대체해 완료 표시하지 않는다.

상태 분리 뒤에도 기존 접수·정원·재신청·만료/사진 파기·수기 취소·배송/수령 API가 새 원본 상태를 일관되게 읽고 쓰도록 연결한다. 새 화면만 옮기고 기존 경로를 두 번째 상태 원본으로 남기지 않는다. 기존 필드/enum 제거는 전체 사용처 전환과 migration 검증 후 별도 변경으로 수행한다. 초기 배포는 새 흐름 활성화 전후의 동작을 명확히 정하며, OFF 설정이 DB 변경을 되돌린다고 가정하지 않는다. 운영에서 새 상태가 기록된 뒤에는 단순 구버전 재배포가 아니라 사전에 검증한 복구 절차를 따른다.

완료 조건: 첫 사용자 흐름과 기존 판매 회귀가 통과하고, 불명확한 과거 주문이 새 작업으로 자동 생성되지 않는다. 테스트 환경 완료와 운영 적용 완료를 별도로 보고한다. 의존: W01~W08; 실제 운영 전환에는 아래 자료/결정 중 해당 범위가 필요하다.

## 3. 실행 순서와 필요한 확인

**첫 묶음: W01 → W02·W03.** 현재 동작의 기준과 새 화면/API 응답을 고정한 후, 저장·명령 기반과 직원 권한을 구현한다. 이 묶음의 산출물은 보호되는 서버 API와 검증된 데이터 기반이다. 사용자에게 완성 화면이 제공됐다고 보고하지 않는다.

**둘째 묶음: W04·W05·W06 → W07.** 돈을 확인한 주문이 모델링 작업으로 생기고, 파일을 등록한 뒤 검수 작업으로 이어지게 한다. W05/W06은 계약이 정해지면 독립 구현할 수 있다. W08의 화면 작업도 확정된 응답 예시로 준비하고 실제 API와 연결한다.

**셋째 묶음: W08 연결 완료 → W09.** 세 계정의 실제 브라우저 흐름을 검증하고 운영 전환 대상과 기존 기능 영향을 확인한다. 여기서 ‘입금 확인부터 검수 인계까지 사용 가능’이라고 판단한다.

작업 소유는 개발 담당자가 백엔드·프론트·검증을 수행하는 계획이다. 이종무와 제작 담당자는 운영 계정/담당자 및 기존 주문의 실제 상태 근거를 제공한다. 일정·인일은 아직 약속하지 않는다. W01의 현재 검사 결과와 파일 업로드 샘플, 과거 주문 검토량이 확인된 뒤 작업별 예상치를 붙인다.

**개발을 진행하면서 준비할 것.** 모델링/검수 담당자의 실제 활성 계정과 역할, 첫 OWNER 지정, 기본 담당자 설정이 필요하다. 테스트는 역할이 구분된 테스트 계정으로 먼저 진행할 수 있다. 실제 모델 원본/STL/3MF의 예시 형식·크기로 W06 계약을 검증한다. 아직 제작 단계가 불명확한 기존 주문은 보완서 Q2 답변과 주문별 확인 근거가 있어야 운영 이전한다.

Q1 수령 장소와 Q3 휴지통 권한은 이번 신규 작업 인계 개발 자체를 막지 않는다. 이번에 신규 수령 장소 정책이나 휴지통 기능을 적용하지 않기 때문이다. 단, 전체 상태 이전 과정에서 해당 데이터/권한까지 바꾸는 변경을 포함한다면 해당 답변을 먼저 반영한다. 노션 토큰, 우체국 결과 파일, 제작 시작 알림 승인 코드는 이 첫 흐름의 개발 선행 조건이 아니다.

**진행 기록 (2026-09-12).** W01의 기준선과 W02~W08의 첫 흐름 구현·화면 연결을 완료했다. W09의 로컬 자동 검증과 운영 적용 절차를 작성했으며, 실제 직원/S3/실물 파일 및 운영 과거 주문 검증은 남아 있다. [구현 결과](../../operations/2026-09-12-first-flow-implementation.md)에 실제 저장 구조 선택, 전체/실DB/브라우저 검사 결과와 검증의 한계를 기록했다. 운영 적용 완료로 표시하지 않는다.
